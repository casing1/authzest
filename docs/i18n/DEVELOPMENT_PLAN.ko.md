# AuthZest 개발 계획

[문서 목차](INDEX.ko.md) · [공개 로드맵](https://github.com/casing1/authzest/issues/1)

## 제품 방향

OSS 과목을 위한 설치형·CLI 중심 FastAPI 소스 인식형 접근통제 분석 도구를 만듭니다.
AI 제공자 없이도 core가 유용하고 반복 가능한 소스 근거를 생성해야 합니다. 선택적 AI는 나중에
그 근거와 한계를 설명할 수 있지만, 추정을 확인된 finding으로 바꾸면 안 됩니다.

기존 로컬 API와 대시보드는 같은 core를 사용하는 선택적 인터페이스입니다. 웹 배포,
네이티브 데스크톱 앱과 새로운 UI 기능은 CLI 단계의 선행 조건이 아닙니다.
`analyzer`, `parser`, `runner`, `codex` 경계는 CLI/API 같은 전달 계층과 분리합니다.

[로드맵 이슈](https://github.com/casing1/authzest/issues/1)는 공개 작업 현황의 기준이며 이 문서는
순서와 완료 조건을 설명합니다. 구현 전에 작업을 범위가 명확한 이슈로 나누고, 완료 조건과
PR 필수 검사를 충족하여 병합된 뒤에만 완료로 표시합니다.

모델 발전을 이유로 core를 자율 agent로 교체하지 않습니다. 모델에 직접 맡기는 것보다 근거 보조 AI가
유용한지는 측정할 가설로 다룹니다. [모델 전략](MODEL_STRATEGY.ko.md)을 참고하세요. 유지하는 사용 사례에
필요한 구문만 확장하고, 새 UI 기능·추가 adapter·범용 Python 인터프리터보다 근거 식별과 평가를 우선합니다.

## 7주 개발 계획

2026-09-10 기준 남은 기간은 약 11–12주이고 과목에 정해진 필수 기능은 없습니다. **개발에는 7주만**
배정하고, **나머지 4–5주는 계획 밖에** 시험기간·지연·최종 제출 준비를 위한 여유로 남깁니다.
아래는 작업 주차 예상이며 연속된 달력 7주나 남은 기간을 모두 채우겠다는 약속이 아닙니다.
시험 중에는 개발을 쉬고 필요하면 범위를 줄입니다.

| 개발 주차 | 제한된 결과물                                  | 완료 기준                                                          |
| --------- | ---------------------------------------------- | ------------------------------------------------------------------ |
| 1         | 신뢰성 기반과 리포트 계약 (#31, #32)           | 재현 가능한 데모, 버전이 있는 진단과 구별되는 등록 근거 테스트     |
| 2         | 라우트 직접 의존성 근거 (#28)                  | 지원 선언·일반 DI·미해석 사례에 소스 기반 예상 결과                |
| 3         | 상속 맥락 (#29)과 작은 정책 label fixture 집합 | 반복 mount 구분, 공개·인증·인가 기대 조건 명시                     |
| 4         | 오프라인 설명 계약 (#33)                       | mock 응답·잘못된 참조·실패 경로·고정 평가 입력 테스트              |
| 5         | 승인된 opt-in adapter 하나와 작은 3모드 비교   | 실제 사용량·반복 변동·인용·한계 기록, 승인 없으면 mock 유지        |
| 6         | 평가에서 영향이 큰 오류 수정과 설치 검증       | 범위·주장이 근거와 일치하고 설치형 CLI smoke 검사 동작             |
| 7         | 일관된 CLI 데모와 제출 근거 확정               | 재현 가능한 데모·검토한 문서·이슈/PR/테스트 이력·릴리스 체크리스트 |

새 preview 릴리스는 검사를 충족할 때만 진행하며 매주 요구하지 않습니다. 5주차 전에 모든 결정론적
finding을 완성할 필요는 없습니다. 첫 AI 작업은 자율 실행이 아닌 설명으로 제한합니다. 일정이 밀리면
추가 규칙·UI·다중 연동·선택적 runner를 줄이고 리포트 계약·검토 가능한 근거·테스트·정직한 평가를
유지합니다. 기능을 늘리려고 시험·제출 여유를 조용히 소진하지 않습니다.

패키지 메타데이터는 아직 `0.1.0a1`이므로 버전 문자열만으로 소스 변경을 구분할 수 없습니다.
[변경 이력](CHANGELOG.ko.md)과 릴리스 태그를 함께 확인하세요.

기본 JSON 출력은 이미 있습니다. 버전이 있는 evidence/finding 스키마, 의존성 분석, 인증·인가
분류, AI 분석과 능동 테스트는 아직 없습니다. `scan`은 대상 애플리케이션이나 Codex를 실행하지
않습니다. 명시적으로 실행한 `doctor`는 진단을 위해 설치된 Codex CLI를 호출할 수 있습니다.

## 선행 작업 — 근거와 진단 계약

- [ ] 버전이 있는 리포트, 호환성 정책과 결정론적 순서를 정의합니다
      ([#32](https://github.com/casing1/authzest/issues/32)).
- [ ] 같은 경로의 반복 mount를 포함해 라우트 등록에 구별되는 안정적 식별자와 원본 handler·app·include
      위치 근거를 부여합니다.
- [ ] 확인한 미해석 사유, 소스/읽기 오류와 제한된 분석 범위를 명시합니다. 모든 미지원 패턴을 검출한다고
      하지 않으며 텍스트/JSON 출력과 CLI 종료 의미를 문서화하고 테스트합니다.

완료 조건: 정상·반복 mount·동적·잘못된 소스·안정적 순서 fixture로 계약을 검증합니다.
계획 갱신으로 구현된 기능이 아닌 다음 작업입니다. #28/#29의 의존성 데이터로 리포트가 커지기 전에
이 선행 단계를 완료합니다.

## 단계 1 — 의존성 근거 수집

1. [ ] 라우트에 직접 선언된 의존성을 수집합니다 ([#28](https://github.com/casing1/authzest/issues/28)).
       매개변수 기본값, 지원하는 인라인 `Annotated`, 데코레이터의 `dependencies`가 대상입니다.
       실제 `Depends`·`Security` import, 별칭과 이름 가림을 구분하고 종류, 대상, 소스 위치,
       선언 위치 종류, 해석 상태와 정적으로 확인한 scopes를 기록합니다.
2. [ ] app/router/`include_router` 근거를 각 라우트 등록에 연결하고 반복 등록별 맥락을 보존합니다
       ([#29](https://github.com/casing1/authzest/issues/29)). #32의 등록 식별자를 사용하며 경로나 handler만으로
       묶지 않고 반복 mount별 맥락을 구분합니다.
3. [ ] 문서화한 범위의 의존성 참조와 중첩 의존성 관계를 해석합니다.
       누락·순환·동적·override·미지원 관계는 추측하지 않고 명시적으로 남깁니다.
4. [ ] 근거가 없다는 사실을 부정적인 보안 판정으로 바꾸지 않도록 미해석 근거와 분석 한계를
       리포트에 드러냅니다.

완료 조건: 지원하는 로컬 fixture에서 예상한 선언 근거와 원본 소스 위치가 CLI/API 리포트에
나타납니다. 기존 route 필드는 호환성을 유지하거나 의도한 스키마 변경을 문서화합니다.
각 이슈에는 검출·일반 비보안 의존성·미해석 사례가 포함되며 대상 소스를 실행하지 않습니다.

## 단계 2 — 해석 기준과 리포트 계약

- [ ] 인증(호출자가 누구인지)과 인가(무엇에 접근할 수 있는지)를 구분합니다.
- [ ] 분류 이름을 정하기 전에 지원하는 근거 규칙, 명시적 공개 endpoint, 미지원 middleware,
      override, 사용자 정의 검사와 객체 단위 정책을 정의합니다.
- [ ] 관찰된 선언을 인증 근거·인가 근거·알 수 없음/불완전 분석과 분리합니다.
      `Depends` 또는 `Security`만으로 보호를 보장하지 않습니다.
- [ ] 선행 리포트 계약을 정책 근거와 향후 finding에 맞춰 확장하고 결정론적 순서·소스 경로 처리·텍스트/JSON
      호환성을 유지합니다.
- [ ] 향후 finding을 도입할 때 선행 CLI 종료 계약을 확장합니다.
      스캔 성공이나 라우트 0개를 보안 통과라고 설명하면 안 됩니다.
- [ ] 예상 정책 표시와 예상 결과를 갖춘 작은 로컬 fixture 모음을 유지합니다.
      공개 endpoint, 일반 DI, 인증 검사, 역할/소유권 시나리오와 미해석 사례를 포함합니다.

완료 조건: 검토자가 소스 근거와 문서화한 규칙으로 모든 보고 상태를 설명할 수 있습니다.
fixture 평가에서 일치·오탐·미탐·unknown 사례를 기록하고, 지원하지 않는 애플리케이션 동작을
조용히 안전하거나 취약하다고 선언하지 않습니다.

현재 동작은 향후 계약과 다릅니다. `scan`은 잘못된 저장소 경로에 종료 코드 2를 반환하지만,
반환된 parse error가 있어도 성공 종료할 수 있습니다. 현재 CLI/API에는 미해석 선언 전용 목록이
없습니다. 보안 판정을 도입하기 전에 이 간극을 처리해야 합니다.

## 단계 3 — 설명 가능한 결정론적 검사

- [ ] 문서화하거나 사용자가 선언한 접근통제 기대 조건을 대상으로 범위가 좁은 소스 검사를
      추가합니다. 인식 가능한 의존성이 없다는 사실만으로 취약점이라고 하지 않습니다.
- [ ] 소스 근거를 연결하고 심각도·확신도·분석 완전성을 구분합니다.
- [ ] 기존 JSON 리포트 위에 사유가 있는 suppression, 회귀 사례와 안정적인 finding 내보내기를 추가합니다.
- [ ] finding 검토 방법과 도구가 증명하지 못하는 범위를 적습니다. 일반적인 런타임 인가 정확성이나
      객체 소유권 보장도 그 한계에 포함됩니다.

완료 조건: 모든 규칙에 검출·비검출·미해석 fixture와 AI 없이 검토할 수 있는 설명이 있습니다.
검사는 로컬 소스를 대상으로 하며 취약점 악용 절차를 생성하거나 실행하지 않습니다.

## 단계 4 — 선택적 AI 보조 설명

이 단계는 안정된 evidence/report 계약 이후이며 선택적 능동 테스트 runner보다 먼저 진행합니다.
작고 명확히 표시된 설명 데모로 완성된 취약점 스캐너를 먼저 만들지 않고도 텀프 목표를 지원할 수 있습니다.

- [ ] 근거에 연결된 설명과 오프라인 평가를 정의합니다
      ([#33](https://github.com/casing1/authzest/issues/33)). 비활성 adapter에 mock 응답·잘못된 참조·실패 테스트를 추가합니다.
- [ ] 제공자를 연결하기 전에 전송할 근거, 데이터 최소화, 비밀정보 제거, 승인, timeout과 취소 동작을 정합니다.
- [ ] 인터페이스 뒤에 명시적으로 활성화하는 adapter 하나를 추가하고 CLI와 App Server 방식은 별도로 평가합니다.
- [ ] AI 제안을 결정론적 결과와 분리하고 근거 참조를 연결하며, AI를 사용할 수 없거나 틀려도 로컬 리포트를 유지합니다.
- [ ] 고정한 사람의 정책 label fixture로 정적 전용·모델 단독·근거 보조 모델을 비교합니다.
      [모델 전략](MODEL_STRATEGY.ko.md)에 따라 별도 평가 사례·반복 실행·실제 사용량·한계를 기록합니다.

완료 조건: 자격 증명·네트워크·AI 없이도 같은 스캔이 유용합니다. 명시적 승인 없이 소스 내용을
외부로 보내지 않고, AI의 추정을 확인된 finding으로 승격하지 않습니다.

## 단계 5 — CLI 릴리스와 OSS 평가

릴리스 준비는 앞 단계와 병행할 수 있습니다. 패키징은 이미 있으므로 새 제품처럼 다시 만들 필요는 없습니다.

- [ ] 기존 프로세스 내부 CLI/API 회귀 검사를 넘어, 설치된 CLI/바이너리로 유지 중인 정책 fixture
      모음을 실행하는 CI 검사를 추가합니다.
- [ ] 지원한다고 안내하는 각 OS/아키텍처에서 깨끗한 환경의 설치·실행·업그레이드를 검증합니다.
- [ ] 허용한 모든 의존성 버전이 같다고 가정하지 말고 실제 테스트한 지원 행렬과 재현 가능한 Python
      의존성 제약/build manifest를 정합니다.
- [ ] 릴리스 노트, 영·한 변경 이력, 태그/패키지 버전과 실제 바이너리 내용을 함께 검증합니다.
      현재 릴리스 스크립트는 태그/버전 표기만 확인하며 변경 이력의 완전성은 검사하지 않습니다.
      빠진 변경 이력/내용 일치 검사는 별도 릴리스 작업으로 자동화합니다.
- [ ] 일관된 기능 단계가 준비되면 검증한 `main` 커밋에서 새로운 preview를 배포합니다.
- [ ] 이슈의 결정, 의미 있는 커밋, PR 논의, CI 근거와 짧고 재현 가능한 데모를 보존합니다.
- [ ] 바이너리를 더 널리 배포하기 전에 서명/공증은 별도로 검토합니다.

완료 조건: 깨끗한 설치에서 문서의 CLI 데모가 동작하고, 릴리스 설명이 다운로드한 바이너리와 일치하며,
변경을 이슈→테스트→PR로 추적할 수 있습니다. 커밋 수를 부풀리거나 문서 수정마다 새 릴리스를 만들지
않습니다. [릴리스 가이드](RELEASING.ko.md)를 참고하세요.

## 이후 선택 사항 — 로컬 회귀 실행

소스 탐색, AI 보조 설명과 초기 CLI 결과물의 선행 조건이 아닙니다.

- [ ] 요청을 보내지 않고 직접 관리·소유하는 로컬 fixture의 검토 가능한 회귀 테스트 계획을 생성합니다.
- [ ] 격리, fixture 한정 범위, timeout, 요청 수 제한과 의도하지 않은 데이터 변경 방지를 갖춘
      명시적으로 승인된 로컬 테스트 harness를 검토합니다.
- [ ] 실행은 opt-in으로 유지하고 `scan`과 분리하며 재현 가능한 결과와 미해결 결과를 기록합니다.

인터넷 대상 스캔, 자율적인 취약점 악용과 임의 저장소 실행은 이 개발 단계에 포함하지 않습니다.
실행 범위를 다시 검토하려면 구현 전에 별도의 설계 이슈로 다룹니다.
