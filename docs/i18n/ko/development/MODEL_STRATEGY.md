# 모델 전략과 평가

[문서 목차](../INDEX.md) · [개발 계획](DEVELOPMENT_PLAN.md)

## 결정

설치형 CLI와 기존 core/adapter 경계를 유지합니다. 특정 GPT 출시를 중심으로 제품을 다시 만들지
않습니다. AuthZest가 제공하려는 가치는 반복 가능한 소스 근거, 명시적 정책 기대 조건, 근거에 연결된
Codex 검토와 사용자가 제안된 개선을 승인한 패치·검증 기록까지 통제하는 흐름입니다.
같은 작업을 모델에 직접 맡기는 것보다 도움이 되는지는 이미 입증한 장점이 아니라 검증할 가설입니다.

Codex 연동과 승인/거절을 포함한 개선 흐름은 단순한 향후 선택적 설명 기능이 아니라 최종 데모의 핵심
목표입니다. 실제 사용은 계속 opt-in입니다. 오프라인 정적 스캔도 유용해야 하며, 소스 공유 허가는
패치 적용이나 테스트 실행 허가가 아닙니다. 아래는 설계 목표이며 실제 adapter·사용자 동의 흐름·패치 실행기가
이미 존재한다는 뜻이 아닙니다.

현재 제품은 제한된 FastAPI 라우트 구문, 라우트 직접 의존성 선언과 app/router/include 상속 맥락을
목록화합니다. 중첩 의존성 그래프 해석, 인가 정확성 판정과 AI adapter 실행은 아직 없습니다.
[소스 전용 예제](../guides/EXAMPLES.md)는 파서 회귀 검사와 데모이며
보안 벤치마크가 아닙니다.

## 안정적인 계약과 교체 가능한 모델

| 계층                | 책임                                                                  | 뜻하지 않는 것                                  |
| ------------------- | --------------------------------------------------------------------- | ----------------------------------------------- |
| Parser와 analyzer   | 결정론적 선언, 원본 위치, 지원하는 등록 맥락                          | 임의 Python의 완전한 이해                       |
| 정책과 리포트       | 관찰한 사실, 사용자 기대 조건, 미해석 근거와 향후 검사를 분리         | 의존성 선언만으로 인증·인가 증명                |
| Codex adapter       | 허용 근거를 검토하고 방어적 테스트·변경을 제안하며 형식과 참조 검증   | 모델의 근거 없는 주장을 확인된 finding으로 승격 |
| 승인과 적용         | 사용자 결정을 정확한 diff·소스 식별값에 연결하고 검증한 제안만 적용   | Codex 도구 허가나 이전 동의가 다른 패치를 승인  |
| 격리 검증           | 별도로 승인한 제한된 소유 fixture 계획을 실행하고 결과·복구 정보 기록 | 테스트 통과가 일반적인 인가 정확성을 증명       |
| CLI와 선택적 API/UI | 같은 core 리포트와 정확한 실패·부분 결과 상태 표시                    | 성공 종료나 라우트 0개가 보안 통과              |

파서를 범용 Python 인터프리터로 확장하지 않습니다. 문서화한 사용 사례와 유지하는 fixture가
필요성을 뒷받침할 때만 구문 지원을 추가합니다. 반복 mount에는 구별되는 등록 식별자와 app/include
위치 근거가 필요하며 URL 경로나 handler 위치만으로는 맥락을 식별할 수 없습니다. 확인한 미해석
사례는 기록하되 모든 미지원 구문을 발견할 수 있다고 주장하지 않습니다.

현재 소스는 [#32: 리포트와 등록 계약](https://github.com/casing1/authzest/issues/32)의 구조화된 진단과
구별되는 등록 근거를 구현하고 [#28: 라우트 직접 선언](https://github.com/casing1/authzest/issues/28)과
[#29: 상속 선언](https://github.com/casing1/authzest/issues/29)으로 스키마 `1.2`까지 확장했습니다.
적용 맥락은 각 선언의 위치/종류를 유지하지만 바깥→안쪽 순서가 런타임 실행 순서 보장은 아닙니다.
의존성 `reference`는 단순/점 연결 이름 구문만 뜻하며 callable 동작 해석이나 보안 분류가 아닙니다.
의존성 근거는 기존 등록 ID 해시에 포함하지 않습니다.
[리포트 계약](../reference/REPORT_CONTRACT.md)은 부분 리포트도 기본 종료 코드 0으로 반환하며
`--strict`를 선택하면 확인한 부분 분석에는 1, 잘못된 저장소 입력에는 2를 반환합니다.
`bounded`는 완전한 분석이나 보안 통과가 아닙니다. 등록 ID는 소스 등록을 식별하며 전체 파일 내용,
소스 revision, 런타임 객체나 패치 승인을 식별하는 값이 아닙니다.

## 실제 연동 이전의 Codex 경계

소스에 [#33: 근거에 연결된 설명과 오프라인 평가](https://github.com/casing1/authzest/issues/33)를 구현했습니다.
[오프라인 계약](../reference/AI_CONTRACT.md)은 최소 입력, 검증한 가설, mock 실패 처리와 고정된
비교 기반을 정의합니다. 정책 기준은 관리자가 승인했으며 예상값은 assistant 작성·코드 대조입니다.
mock 지표는 모델 품질의 근거가 아닙니다.
그 다음 [#35: 사용자 승인형 Codex 개선 흐름](https://github.com/casing1/authzest/issues/35)에서
제안/승인 계약, adapter, 승인된 적용과 격리 검증을 다루며 #33만으로 전체 흐름이 구현되는 것은 아닙니다.
기본 스캔과 CI에는 제공자 호출, 자격 증명, 구독이나 유료 모델이 필요하지 않습니다.

나중에 추가할 opt-in adapter는 명시적 데이터 공유 승인과 허용 입력 범위 확인이 필요합니다.
저장소 텍스트는 신뢰하지 않는 데이터이며 모델에 도구나 접근 권한을 부여하는 지시가 아닙니다.
소스 내용을 최소화하고 비밀정보를 처리하며 timeout, 취소, 잘못된 출력, 제공자 사용 불가와
지원하지 않는 참조의 동작을 정의합니다. adapter가 실패해도 로컬 리포트는 유지해야 합니다.

각 설명을 제공한 근거 식별자와 대조하고 추정한 정책을 사람이 선언한 정책과 분리합니다.
공개 endpoint와 일반적인 의존성 주입은 정상 사례이며, 인식 가능한 인가 근거가 없다는 사실만으로
취약점이라고 하지 않습니다.

adapter가 생기면 제공자/모델을 설정으로 선택하게 합니다. 실제 반환된 모델 식별자, prompt/adapter/report
버전, 소스 revision 또는 내용 식별값, 허용 입력 목록과 확보 가능한 실제 사용량·지연 시간을 기록합니다.
새 모델로 조용히 바꾸거나 없는 사용량을 만들어내지 않습니다. 민감한 소스와 자격 증명은 telemetry에서
제외합니다. CLI와 App Server는 인터페이스 뒤의 연동 선택지이며 텀프에서 동시에 구현할 요구가 아닙니다.

## 계획된 제안·승인·검증 계약

#46의 [오프라인 제안/결정 계약](../reference/PROPOSAL_CONTRACT.md)은 연결된 산출물·미리보기·내부
결정 검사만 구현합니다. 코드를 생성하거나 소스를 수정하지 않으며 아래의 실제 파일/철회/원자적 적용
검사를 대신하지 않습니다.

최소 최종 데모는 직접 소유·관리하는 fixture 하나에서 다음 단계를 구분해 보여주는 것입니다.

1. 소스 근거와 사람이 선언한 정책을 수집하고 Codex에 공유할 입력을 명시적으로 선택·승인합니다.
2. 격리된 임시 workspace에서 근거에 연결된 검토, 방어적 회귀 테스트 초안과 diff 제안을 만듭니다.
   원본 worktree를 보존하며 제안 중에는 스캔한 애플리케이션을 실행하지 않습니다.
3. 이유, 근거 참조, 대상 파일, 정확한 diff, 소스 revision/내용 식별값과 예정된 검증 계획을 보여줍니다.
   사용자는 승인·거절·취소할 수 있으며 응답하지 않았다고 승인으로 간주하지 않습니다.
4. 제안 식별값과 소스 사전 조건을 다시 확인하고 승인된 diff만 적용합니다. 소스나 제안 diff가 바뀌면
   오래된 승인을 거부하고 기존 사용자 변경을 덮어쓰지 않습니다.
5. 검토한 검증 계획은 별도로 허가를 요청하고 제한된 격리 소유 fixture 환경에서만 실행합니다.
   실행 내용, 종료 상태, 통과/실패/미실행 검사와 남은 불확실성을 기록합니다.
6. 승인된 제안, 결정, 전후 식별값과 결과를 소스 정보가 최소화된 변경 기록으로 보존합니다.
   사전 조건이 유지될 때만 복구를 제공하고 그렇지 않으면 관련 없는 작업을 초기화하지 않고 충돌을 알립니다.
   실패했거나 실행하지 않은 테스트는 성공한 수정이 아닙니다.

거절, 취소, 잘못된 인용·제안, 제공자 실패, 오래된 승인, 기존 사용자 변경, 변경된 검증 계획,
테스트 실패와 복구 충돌에 대한 오프라인 계약 테스트가 필요합니다. 생성된 테스트와 저장소 내용은
신뢰하지 않는 데이터이며 허용 파일·도구·네트워크·실행 범위를 넓히지 못합니다.
검증 계획이 바뀌면 실행을 다시 승인받습니다. 취약점 악용 PoC 생성, 자율 공격 흐름과 임의 저장소
실행은 계획에 포함하지 않습니다.

App Server는 Codex 설정에 따라 명령/파일 변경 승인을 요청할 수 있지만 모든 편집 전에 확인을
보장하지는 않습니다. 따라서 AuthZest는 전달 계층/도구 허가와 별개로 정확한 제안별 승인 단계를
가져야 합니다. 제품을 사용하기 위해 세션 전체의 포괄 승인을 요구하지 않습니다.
이는 문서의 승인 동작을 바탕으로 한 제품 설계이며 AuthZest가 이미 구현한 App Server 기능이 아닙니다.
[Codex App Server 승인 문서](https://learn.chatgpt.com/docs/app-server#approvals).

## 제품 가설 검증

prompt를 조정하기 전에 직접 소유하는 작은 로컬 fixture와 예상 정책 label을 사람이 검토하고 고정합니다.
일반 DI, 의도적 공개 라우트, 관련 접근통제 선언, 반복 mount, 불완전 입력과 미지원 패턴을 포함합니다.
예상 정답은 모델 입력에서 제외하고 일부 사례는 prompt 개발이 아닌 평가용으로 남깁니다.

같은 작업과 허용 소스/정책 범위로 세 모드를 비교합니다.

1. AI 없는 정적 근거.
2. AuthZest가 추출한 근거 없이 허용 소스와 정책을 모델에 직접 제공.
3. 같은 모델에 같은 범위와 AuthZest 근거를 함께 제공.

두 AI 모드의 모델과 작업 지시를 비교 가능하게 유지하고, 불가피한 입력 차이를 기록하며 같은 비용이라고
주장하는 대신 실제 token 사용량을 기록합니다. 비결정론적 모드는 반복 실행합니다. 정적 전용 모드는 설명
작업에 답하지 못할 수 있으므로 답변 보류를 정답으로 세지 않고 작업 지원 범위와 정확성을 나눠 보고합니다.

라우트/선언의 정확성과 지원 범위, 올바른 소스 인용, 근거 없는 주장, 정책 일치, 미해석 결과, 반복 실행
변동, 지연 시간, 실제 사용량과 사람의 검토 노력을 측정합니다. 승인/적용 흐름은 별도로 평가합니다.
정확히 승인된 변경만 적용하는지, 거절·오래된 승인에서 변경하지 않는지, 사용자 변경을 보존하는지,
검증 실패를 정확히 보고하고 안전하게 복구하는지 확인합니다. 테스트 통과는 해당 테스트와 fixture에
대한 근거이며 일반적인 보안 보장이 아닙니다. 종합 점수와 함께 분모, fixture 한계와
대표 오류를 보고합니다. 라우트가 많거나 unknown이 적다는 사실만으로 더 좋은 보안 분석은 아닙니다.
목록화 fixture와 나중에 추가할 정책 label 평가 집합을 구분합니다.

근거 계약과 초기 의존성 fixture가 준비되면 작은 비교를 시작할 수 있으며, 완성된 결정론적 finding 엔진이
선행 조건은 아닙니다. 근거 보조 모드가 도움이 되지 않으면 agent 자율성을 늘리는 대신 주장을 좁히거나
작업 흐름을 수정합니다.

## 설계의 참고 근거

2026-09-10에 공식 문서를 확인했습니다. 모델 기능과 권장은 변하므로 교체 가능한 경계에서 모델을 선택합니다.
이는 우리의 구조적 판단이며 AuthZest 성능이 입증됐다는 뜻은 아닙니다.
[OpenAI 모델 가이드](https://developers.openai.com/api/docs/guides/latest-model).

작업별 데이터셋, 전문가 label, 명시적 지표, 비교와 반복 평가를 위 평가 과정의 참고로 삼았습니다.
[OpenAI 평가 가이드](https://developers.openai.com/api/docs/guides/evaluation-best-practices).

App Server 문서의 인터페이스와 관리형 인증 흐름은 나중에 검토할 수 있습니다. 문서를 읽는 것만으로
adapter가 활성화되거나 저장소 데이터를 전송할 권한을 얻는 것은 아닙니다.
[Codex App Server 문서](https://learn.chatgpt.com/docs/app-server).
