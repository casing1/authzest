# 생성 수정 생명주기 — 순수 모의 전용

[문서 목차](../INDEX.md) · [오프라인 복사 세션](GENERATED_REPAIR_SESSION.md) ·
[검증 기반](GENERATED_REPAIR_VERIFICATION.md)

## 범위 — 2026-11-12 KST

[#152](https://github.com/casing1/authzest/issues/152)의 또 다른 부분 오프라인 단계입니다.
비공개 생명주기 모델은 수용한 **T → 새 A/B** 컨테이너 순서를 제한된 모의 이벤트로 표현합니다.
엔진 전송·Docker 명령·프로세스 콜백·네트워크·AI 요청·생성 코드 실행·파일 쓰기는 없습니다.
복사 세션·CLI·API·UI와 연결하지 않으며 #152는 열린 상태입니다.

기존 미리보기에는 실제 이미지·엔진·launcher·relay 식별자가 없고 제안한 자원 설정도 강제하지
않습니다. 기본 실행기 준비는 계속 비활성입니다. 모델의 합성 식별자·구성은 테스트 데이터이지
검사한 로컬 이미지·런타임 설정이 아닙니다. 기존 등록 worker·프롬프트·의존성·패키지 버전·공개
명령은 바꾸지 않습니다.

## 모의 순서

[비공개 모듈](../../../../src/authzest/runner/_generated_repair_lifecycle.py)은 데이터 전용 의도를
내보내고 현재 의도에 대한 크기·필드 제한 응답만 받습니다. 이름·nonce·예상 합성 구성은 모델이
정하며 이벤트가 실행 파일이나 대상을 선택할 수 없습니다. 결과 읽기는 과거 기록이며 현재 시각·
파일·컨테이너의 새 관찰이 아닙니다.

`GeneratedRepairLifecycleModel(clock=...)`은 `next_intent()`, `reply(event)`, `cancel()`,
`result()`를 제공합니다. 대기 중 의도에는 현재의 제한된 응답 하나가 필요하며 다음 의도를 요청해
모의 dispatch를 반복할 수 없습니다. execute·apply·restore·import API는 없습니다.
Python 호출자와 동기 시계는 신뢰하는 구성요소이지 이 interface가 격리하는 대상이 아닙니다.

- T는 애플리케이션·테스트 입력을 사용하는 생성 테스트 역할입니다. 모의 종료·제거가 확인된 뒤에만
  독립 애플리케이션·relay 쌍을 생성합니다.
- A는 생성 테스트 없는 애플리케이션, B는 소스·테스트 입력 없이 A의 정확한 모의 네트워크 공간만
  공유하는 관리형 relay 역할입니다.
- 역할마다 소유 이름 기록 확인 → 정지 상태 생성 → 정확한 모의 식별자·구성 검사 → 출력 연결 →
  시작 순서를 요구합니다.
- 생성이 모호하면 사전에 기록한 정확한 이름으로 대조합니다. 외부 nonce·이미지·구성을 정리
  대상으로 삼지 않습니다. 시작이 모호하다고 종료된 것은 아니며 검증된 정확한 ID에만 정리 의도를 냅니다.

이미지 소유 HTTP relay 구현이나 생성 pytest 보고서 가져오기는 없습니다. T의 종료·보고는
신뢰할 수 없는 보조 데이터입니다. before 테스트는 의도적인 소유권 누락 때문에 실패할 수 있으며
종료 코드만으로 재현·수정을 입증하지 않습니다. 별도의 관리형 비교기도 전달된 데이터만 비교하며
인증된 런타임 사실로 취급하지 않습니다.

## 공유 예산과 실패

공유 단계 40초와 그 안의 누적 시작·준비 최대 10초를 모의합니다. 준비에는 A의 마지막 준비 응답만
아니라 각 역할의 기록·생성·검사·출력 연결·시작 구간과 A의 준비가 포함됩니다. 정상 T 정리는 원래
단계 시간 안에 포함됩니다. 최종·실패 정리는 남은 역할이 공유하는 추가 절대 만료 10초를 사용하며
게스트마다 만료를 갱신하지 않습니다. 모든 역할의 stdout/stderr 합계는 최대 256KiB입니다.
이는 모의 정책 제한이지 측정한 Docker 기능이나 파일시스템·daemon·kernel 전체 시간 보장이 아닙니다.

잘못되거나 역행한 시계, 재사용, 잘못된 순서·응답, 기록·출력 수집 오류, 시간 초과, 출력 초과,
signal, OOM, 취소는 모의 성공이 될 수 없습니다. 최초 원인과 정리 불확실성을 따로 보존합니다.
클라이언트 종료나 EOF가 컨테이너 종료·제거를 입증하지 않습니다. 정리가 불확실하면 후속 모의
작업을 막습니다.

실제 stdout/stderr·소스·계정 데이터는 수집하지 않습니다. 제한된 과거 요약은 영속 엔진 기록·실행
증명·동의 영수증·재개 가능한 체크포인트가 아닙니다.

## 런타임·적용 권한 없음

정상 순서가 끝나도 **모의**입니다. 런타임 미호출, 실행 `not-run`, 기준 `not-established`, 인가
`unknown`, `verified_fix: false`를 유지합니다. 직렬화한 결과로 세션 before 근거 확립·소스 diff
수용·파일 적용·복구를 허용하지 않습니다. 런타임 어댑터 주입·호스트 pytest 대체도 없습니다.

관리형 테스트는 가짜 이벤트·시계를 사용하고 실제 실행·네트워크 경계를 막습니다. 테스트 통과는
모의 순서·실패 처리를 검증한 것이지 실제 격리·출력 수집·자원 강제·생성 수정의 검증이 아닙니다.

검토한 고정 이미지·로컬 엔진, 실제 정지 생성 검사, staging 파일 연결, 제한된 출력·relay 수집,
정확한 객체 정리가 후속 통합 작업입니다. 이후 별도 범위의 설치형 before/after 관찰·CLI 통합·
읽기 전용 결과 UI가 과목 릴리스 근거를 완성해야 합니다. 이번 단계는 릴리스·실제 PoC 재현·
검증된 수정·이슈 완료 결정이 아닙니다.
