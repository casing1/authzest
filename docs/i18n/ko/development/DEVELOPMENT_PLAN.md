# AuthZest 개발 계획

[문서 목차](../INDEX.md) · [공개 로드맵](https://github.com/casing1/authzest/issues/1)

## 제품 방향

OSS 과목을 위한 설치형 CLI 중심 FastAPI 소스 근거 도구를 만듭니다. 핵심 제출물은 직접 소유한
접근통제 사례 하나에서 소스 근거 → 검토한 방어적 재현/사례 계획 → Codex 수정 추천 또는 타당한
변경 없음 → 정확한 diff 승인/거절 → 승인한 새 복사본 적용 → 별도 승인한 관찰 → 확인 가능한
복구 기록을 연결하는 것입니다. Codex는 선택적 설명 부가 기능이 아니라 핵심 목표이며 AI 계정 없이도
정적 스캔이 유용해야 합니다.

parser/analyzer, Codex adapter, runner, 표현 계층의 경계를 유지합니다. 기존 로컬 API/React
대시보드는 선택적 정적 목록 화면이며 아직 Codex 결정을 표시하지 않습니다. AI GUI·배포·두 번째
adapter보다 CLI 사용성을 먼저 개선합니다. 모델 발전 때문에 자율 에이전트나 범용 Python
인터프리터로 재작성하지 않습니다. 근거 보조의 가치는 이미 입증한 장점이 아닌 측정할 가설입니다.
[모델 전략](MODEL_STRATEGY.md)을 참고하세요.

## 핵심 수용 조건과 방어적 PoC

- [ ] 정확한 사례 검토와 고정 검사 계획 계약 수용 (#77); 데이터 API는 있으나 기록된 10개 예상값의 관리자 검토는 필요합니다.
- [x] 읽기 쉬운 CLI 결과·기록 보존·텍스트/JSON 스트림 문서화 수용 (#79 / PR #90).
- [ ] 유지하는 고정 정책 worker가 새 별도 승인 아래 예상값/관찰값 결과 제공 (#80).
- [ ] 검토한 제한적 방어 재현과 근거 연결 수정/변경 없음 수용 (#81).
- [ ] 설치형 통합 흐름·실패/거절/사용자 수정/복구·필수 리뷰 통과 (#82), 그때만 #35 종료.
- [ ] 독립 정답 검토와 측정 평가 또는 확보하지 못한 근거 명시 (#84).
- [ ] 정확한 배포 주장·재현 시연·과목 근거 고정 수용 (#83/#85).

PoC는 명시적으로 소유한 순수 정책의 로컬 합성 **방어적 회귀 재현**이며 외부 공격이나 AI 작성
Python/shell 실행이 아닙니다. 모델 사례는 고정 검토 decoder/harness가 소비하는 데이터입니다.
순수 정책 관찰은 HTTP 인증·의존성·DB·실제 endpoint 강제를 검사하지 않습니다.
자식 프로세스는 OS/네트워크 sandbox가 아닙니다.

현재 올바른 정책에는 변경 없음/unknown도 허용해야 합니다. 부정 사례가 필요하면 의도적 오류를 가진
test-only 변형을 명확히 표시해 구현 전에 관리자 설계 검토를 제안합니다.
패치를 만들기 위해 생산 코드 취약점을 꾸며내지 않습니다.

소스 공유·정확한 사례 정답 검토·정확한 diff 승인/적용·변경 전후 검사·복구는 별도로 연결된 결정입니다.
관련 소스/사례/계획이 바뀌면 새 결정이 필요합니다. 계획 승인·도구 허가·과거 실제 실행이 대신할 수 없습니다.
적용/검사/복구/실패/미실행/불명을 구별하고 원본과 이후 사용자 변경을 보존합니다.

## 일정: 기존 개발 7주를 유지

2026-09-10 합의한 **개발** 7주에는 이미 수행한 작업이 포함되며 이번 점검에서 다시 시작하지
않습니다. 당시 남은 달력 기간 추정은 과거 기록이지 현재 제출일이 아닙니다.
실제 과목 제출일/평가기준을 확인한 뒤에만 기한을 추가합니다.

기반/근거/오프라인 계약과 일부 실제 연동이 초기 개발 예산을 이미 사용했습니다. 남은 작업 세션은
핵심/사용성 gate, 평가·실패·설치 확인, 시연 고정에 사용합니다. 시험/지연/제출 여유는 별도로 보존하고
선택 기능으로 채우지 않습니다. 시간이나 제공자 승인이 부족하면 선택 범위를 줄이고 실제/검사 공백을
정확히 보고합니다. 미완성 핵심을 완료라고 하지 않습니다.

## 명시적으로 후순위인 범위

범용 중첩 의존성/callable 해석·광범위 인증/보안 분류·다중 파일/기존 checkout 트랜잭션·임의
저장소/앱/생성 코드 실행·추가 adapter·AI 대시보드/배포·서명/공증은 제한된 과목 핵심의 선행 조건이
아닙니다. 다시 고려하려면 별도 근거 있는 이슈를 만듭니다. 정적 parser의 유지 회귀 검사는 필요하지만
완전한 결정론적 취약점 엔진을 완성해야 Codex 개선 시연을 할 수 있는 것은 아닙니다.

## 작업 규칙

명확한 이슈 → 짧은 브랜치 → 의미 있는 구현/테스트 → 영한 문서 → PR → 정확한 head의 필수 CI와
리뷰 대화 해결 → merge commit 순서로 진행합니다. 모든 이슈/PR에는 casing1·기존 적절한 라벨·
실제 확인한 마일스톤을 넣되 #1은 전체 단계를 가로지르는 예외입니다.
과거 작성자/승인을 보존하고 실제 조건 충족과 병합 후 완료 처리하며 커밋 수를 부풀리지 않습니다.

영어 문서는 한국어를 제공하고 루트 README는 추가로 일본어/러시아어도 제공합니다.
사용 안내는 구현된 동작만 반영하고 링크/명령/상태/한계를 동기화합니다. 계획 변경이 유료/수동 리뷰,
소스 전송·사례 검토·패치/실행·발행 승인이 되지 않습니다.
[기여 안내](../CONTRIBUTING.md)와 [브랜치 규칙](BRANCH_RULES.md)을 참고하세요.
