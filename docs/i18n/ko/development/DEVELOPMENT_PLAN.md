# AuthZest 개발 계획

[문서 목차](../INDEX.md) · [공개 로드맵](https://github.com/casing1/authzest/issues/1)

## 제품 방향

OSS 과목을 위한 설치형 CLI 중심 FastAPI 소스 근거 도구를 만듭니다. 핵심 제출물은 직접 소유한
접근통제 사례 하나에서 소스 근거 → 검토한 방어적 재현/사례 계획 → Codex 수정 추천 또는 타당한
변경 없음 → 정확한 diff 승인/거절 → 승인한 새 복사본 적용 → 별도 승인한 관찰 → 확인 가능한
복구 기록을 연결하는 것입니다. Codex는 선택적 설명 부가 기능이 아니라 핵심 목표이며 AI 계정 없이도
정적 스캔이 유용해야 합니다.

parser/analyzer, Codex adapter, runner, 표현 계층의 경계를 유지합니다. 기존 로컬 API/React
대시보드는 선택적 정적 목록 화면이며 아직 Codex 결정을 표시하지 않습니다. AI GUI·배포·두 번째
adapter보다 CLI 사용성을 먼저 개선합니다. 모델 발전 때문에 자율 에이전트나 범용 Python
인터프리터로 재작성하지 않습니다. 근거 보조의 가치는 이미 입증한 장점이 아닌 측정할 가설입니다.
[모델 전략](MODEL_STRATEGY.md)을 참고하세요.

정확한 테스트 전용 소유자 비교 생략 시나리오·소스 쌍·어시스턴트 작성 예상값 8개를 승인했습니다.
작성 이력은 어시스턴트 작성으로 유지하며 이 결정은 인증된 승인 권한, 관찰 또는 실행 동의가 아닙니다.

[PR #101](https://github.com/casing1/authzest/pull/101)에서 도입한 소스 구현은 전체 고정
소스/기준/가정/케이스 데이터, 별도 검토 기록 binding과 host가 도출한
단일 파일 diff를 포함하는 별도 [등록 수정 쌍 API](../reference/OWNER_POLICY_REPAIR_PAIR.md)를
제공합니다. 이 미출시 순수 API는 제공자를 호출하거나 정책을 import/평가하거나
파일/네트워크에 접근하거나 프로세스를 실행하거나 패치를 적용하거나 관찰을 생성하지 않습니다.
상태는 provider `0`, 실행/적용/복구 `not-run`, 전후 관찰 null, 비교 `not-evaluated`, 인가
`unknown`을 유지합니다. 기존 S1 스키마 `1.0`/`empty-v1`과 #80 worker는 그대로 둡니다.
모델 공유·고정 전후 관찰·새 복사본 적용/복구는 별도 후속 설계와 승인을 받습니다. 유한한 합성
회귀를 생산 코드 취약점이나 평가셋으로 취급하지 않으며 전체 #81은 계속 미완료입니다.

PR #102는 고정 `before`/`after` 요청, 엄격한 등록 변경/변경 없음/불명 결과, host 도출 diff
선택을 갖춘 별도 오프라인 수정 추천 계약을 전달했습니다. 다음 소스 단계는 별도
`codex-owner-repair` 명령으로 이를 연결합니다. 전체 소스/프롬프트/스키마/설정 미리보기와 새 정확한
공유 결정 후에 고정 App Server를 한 번 시도하며 미리보기 전용 경로는 오프라인입니다.
Host 전송 metadata는 서명된 제공자 출처가 아니며 검증한 설명/예상 효과는 관찰된 정책 동작이
아닙니다. 거절·과거 공유·scripted 응답 오프라인 검사가 별도 승인한 실제 수용에 선행합니다.
고정 전후 worker 관찰과 새 복사본 적용/복구는 이후 단계이며 기존 `codex-owner-review`, S1,
#80 worker는 그대로 유지합니다.

구현된 #79는 사람이 읽는 기본 출력과 명시적 JSON 호환성을 정의합니다. JSON 모드의 stdout에는 최종 결과
하나, 대화형 미리보기/프롬프트/진행은 stderr, 미리보기 전용 JSON은 전체 미리보기 하나를 출력합니다.
공유 전에 식별값에 연결된 전체 내용을 유지하며 요약만으로 대신하지 않습니다.
안내 문서에는 기본 stdout이 그대로라는 주장 대신 기본 출력 변경/자동화 전환을 명시합니다.

다음 프리릴리즈는 구현 범위/한계를 명시한다면 #35 전체 완료를 기다리지 않고 #77/#79 이후 낼 수
있습니다. 그래도 #83 자체 검사가 필요하며 문서 PR이나 mock 성공은 릴리즈 gate가 아닙니다.

## 핵심 수용 조건과 방어적 PoC

- [x] 2026-10-09 KST에 정확한 사례 예상값 10개 검토를 별도 기록 (#77); 오프라인 계약은 있으나 계획은 실행 불가이며 실행 동의는 별도입니다.
- [x] 읽기 쉬운 CLI 결과·기록 보존·텍스트/JSON 스트림 문서화 수용 (#79 / PR #90).
- [x] #80 소스 전용 고정 harness를 [PR #97](https://github.com/casing1/authzest/pull/97)로 전달했고 2026-10-15 KST에 정확한 head CI·코드/보안 리뷰를 완료했습니다. 소스 관찰은 endpoint 인가 근거가 아닙니다.
- [ ] 검토한 제한적 방어 재현과 근거 연결 수정/변경 없음 수용 (#81).
- [ ] 설치형 통합 흐름·실패/거절/사용자 수정/복구·필수 리뷰 통과 (#82), 그때만 #35 종료.
- [ ] 독립 정답 검토와 측정 평가 또는 확보하지 못한 근거 명시 (#84).
- [ ] 정확한 배포 주장·재현 시연·과목 근거 고정 수용 (#83/#85).

PoC는 명시적으로 소유한 순수 정책의 로컬 합성 **방어적 회귀 재현**이며 외부 공격이나 AI 작성
Python/shell 실행이 아닙니다. 모델 사례는 고정 검토 decoder/harness가 소비하는 데이터입니다.
순수 정책 관찰은 HTTP 인증·의존성·DB·실제 endpoint 강제를 검사하지 않습니다.
자식 프로세스는 OS/네트워크 sandbox가 아닙니다.

현재 올바른 정책에는 변경 없음/unknown도 허용해야 합니다. 명확히 표시한 의도적 오류의 테스트 전용
정확한 쌍과 예상값 8개는 2026-10-19 KST에 검토했지만, 이 검토는 런타임 관찰이나 패치 적용을
허용하지 않습니다. 패치를 만들기 위해 생산 코드 취약점을 꾸며내거나 변경된 바이트/케이스까지
이 승인을 확장하지 않습니다.

소스 공유·정확한 사례 정답 검토·정확한 diff 승인/적용·변경 전후 검사·복구는 별도로 연결된 결정입니다.
관련 소스/사례/계획이 바뀌면 새 결정이 필요합니다. 계획 승인·도구 허가·과거 실제 실행이 대신할 수 없습니다.
적용/검사/복구/실패/미실행/불명을 구별하고 원본과 이후 사용자 변경을 보존합니다.

## 일정: 기존 개발 7주를 유지

2026-09-10 합의한 **개발** 7주에는 이미 수행한 작업이 포함되며 이번 점검에서 다시 시작하지
않습니다. 당시 남은 달력 기간 추정은 과거 기록이지 현재 제출일이 아닙니다.
실제 과목 제출일/평가기준을 확인한 뒤에만 기한을 추가합니다.

기반/근거/오프라인 계약과 일부 실제 연동이 초기 개발 예산을 이미 사용했습니다. 남은 작업 세션은
핵심/사용성 gate, 평가·실패·설치 확인, 시연 고정에 사용합니다. 시험/지연/제출 여유는 별도로 보존하고
선택 기능으로 채우지 않습니다. 시간이나 제공자 승인이 부족하면 선택 범위를 줄이고 실제/검사 공백을
정확히 보고합니다. 미완성 핵심을 완료라고 하지 않습니다.

## 명시적으로 후순위인 범위

범용 중첩 의존성/callable 해석·광범위 인증/보안 분류·다중 파일/기존 checkout 트랜잭션·임의
저장소/앱/생성 코드 실행·추가 adapter·AI 대시보드/배포·서명/공증은 제한된 과목 핵심의 선행 조건이
아닙니다. 다시 고려하려면 별도 근거 있는 이슈를 만듭니다. 정적 parser의 유지 회귀 검사는 필요하지만
완전한 결정론적 취약점 엔진을 완성해야 Codex 개선 시연을 할 수 있는 것은 아닙니다.
