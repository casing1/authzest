# AuthZest 개발 계획

[문서 목차](../INDEX.md) · [공개 로드맵](https://github.com/casing1/authzest/issues/1)

## 제품 방향

OSS 과목을 위한 설치형·CLI 중심 FastAPI 소스 인식형 접근통제 검토·개선 도구를 만듭니다.
최종 데모는 소스 근거를 Codex에 연결하고, 검토 가능한 방어적 회귀 테스트·패치 제안,
명시적인 승인/거절, 승인된 패치만 적용, 별도로 승인한 격리 검증과 변경 기록까지 보여줘야 합니다.
Codex 연동은 나중에 선택적으로 추가할 설명 기능이 아닌 핵심 제품 목표입니다.
전체 흐름은 미완료입니다. #33/#46/#48은 오프라인 단계이며 [#50](../guides/CODEX_FIXTURE.md)은
opt-in 소유 fixture App Server 초안을 추가하며 한 fixture의 실제 초안·적용·복구 확인 1회가 성공했습니다.
후속 [#54 확인](../guides/RUNTIME_VERIFICATION.md)에서는 별도로 승인한 고정 런타임 검사와 복구까지
완료했습니다. 이 좁은 흐름은 공개된 alpha.3에 포함되지만 더 넓은 #35 완료 조건, 생성 회귀 테스트
초안과 일반 저장소 연동은 미완료입니다.

정적 core는 AI 제공자 없이도 유용하고 반복 가능한 근거를 생성해야 합니다. Codex는 실행할 때마다
명시적으로 선택하며 외부 데이터 공유, 특정 패치 적용, 검증 계획 실행은 각각 별도의 허가가 필요합니다.
AI가 생성했다는 이유만으로 추정을 확인된 finding으로 바꾸면 안 됩니다.

기존 로컬 API와 대시보드는 같은 core를 사용하는 선택적 인터페이스입니다. 웹 배포,
네이티브 데스크톱 앱과 새로운 UI 기능은 CLI 단계의 선행 조건이 아닙니다.
`analyzer`, `parser`, `runner`, `codex` 경계는 CLI/API 같은 전달 계층과 분리합니다.

[로드맵 이슈](https://github.com/casing1/authzest/issues/1)는 공개 작업 현황의 기준이며 이 문서는
순서와 완료 조건을 설명합니다. 구현 전에 작업을 범위가 명확한 이슈로 나누고, 완료 조건과
PR 필수 검사를 충족하여 병합된 뒤에만 완료로 표시합니다.

모델 발전을 이유로 core를 자율 agent로 교체하지 않습니다. 모델에 직접 맡기는 것보다 근거 보조 AI가
유용한지는 측정할 가설로 다룹니다. [모델 전략](MODEL_STRATEGY.md)을 참고하세요. 유지하는 사용 사례에
필요한 구문만 확장하고, 새 UI 기능·추가 adapter·범용 Python 인터프리터보다 근거 식별과 평가를 우선합니다.

## 7주 개발 계획

2026-09-10 기준 남은 기간은 약 11–12주이고 과목에 정해진 필수 기능은 없습니다. **개발에는 7주만**
배정하고, **나머지 4–5주는 계획 밖에** 시험기간·지연·최종 제출 준비를 위한 여유로 남깁니다.
아래는 작업 주차 예상이며 연속된 달력 7주나 남은 기간을 모두 채우겠다는 약속이 아닙니다.
시험 중에는 개발을 쉬고 필요하면 범위를 줄입니다.

| 개발 주차 | 제한된 결과물                                        | 완료 기준                                                            |
| --------- | ---------------------------------------------------- | -------------------------------------------------------------------- |
| 1         | 신뢰성 기반과 리포트 계약 (#31, #32)                 | 재현 가능한 데모, 버전이 있는 진단과 구별되는 등록 근거 테스트       |
| 2         | 라우트 직접 의존성 근거 (#28)                        | 지원 선언·일반 DI·미해석 사례에 소스 기반 예상 결과                  |
| 3         | 상속 맥락 (#29)과 작은 정책 label fixture 집합       | 반복 mount 구분, 공개·인증·인가 기대 조건 명시                       |
| 4         | #33 이후 오프라인 제안·승인 계약                     | mock 응답·잘못된 참조·정확한 diff 승인·변경된 입력·거절 경로 테스트  |
| 5         | opt-in Codex 연동 하나와 작은 소유 fixture 개선 흐름 | 검토 → 승인/거절 → 승인된 패치 → 별도로 승인한 격리 검증 시연        |
| 6         | 실패·복구 사례, 설치와 작은 3모드 평가               | 테스트 실패·오래된 승인·사용자 변경·복구 처리, 실제 사용량·한계 기록 |
| 7         | 일관된 CLI 데모와 제출 근거 확정                     | 재현 가능한 데모·검토한 문서·이슈/PR/테스트 이력·릴리스 체크리스트   |

새 preview 릴리스는 검사를 충족할 때만 진행하며 매주 요구하지 않습니다.
[v0.1.0-alpha.2](https://github.com/casing1/authzest/releases/tag/v0.1.0-alpha.2), 패키지 `0.1.0a2`는
#28/#29와 릴리스 이슈 #39 이후 발행됐습니다. 해당 커밋의 영한 변경 기록 검사, 3개 OS 빌드와 별도
다운로드 산출물 fixture 검사가 통과했습니다. [릴리스 기록](../releases/RELEASING.md)을 참고하세요.
후속 [v0.1.0-alpha.3](https://github.com/casing1/authzest/releases/tag/v0.1.0-alpha.3), 패키지
`0.1.0a3`는 정확한 main/tag 빌드와 새 다운로드 검사를 거쳐 2026-09-12에 발행됐으며 이후 공개
산출물의 checksum·내용도 대조했습니다. 스키마 `1.2`를 유지하며 제한된 Codex fixture 흐름을 추가합니다.
일반 사용자 기기의 깨끗한 설치·업그레이드는 미검증이며 이후 릴리스도 각각 검사가 필요합니다.
7주 계획을 다시 시작하거나 시험 여유를 사용하지 않습니다. 5주차 전에 모든 결정론적
finding을 완성할 필요는 없습니다. 범용 자율 스캐너가 아니라 직접 소유·관리하는 fixture 하나에서
사용자가 승인하는 제한된 개선 흐름을 시연합니다. 제공자 호출이나 실행 승인이 없으면 mock 데모임을
명시하고 실제 연동은 미완료로 보고합니다. 일정이 밀리면 추가 규칙·UI·다중 연동·더 넓은 실행 지원을
줄이고 핵심 승인 흐름·검토 가능한 근거·테스트·정직한 평가를 유지합니다.
기능을 늘리려고 시험·제출 여유를 조용히 소진하지 않습니다.

아직 구현되지 않았습니다.

애플리케이션에서 최대 한 턴을 요청하며 한 소유 fixture의 실제 확인은 성공했습니다. 유지하는 debug 설정 변경만 허용하고
복사본 적용·복구는 별도 결정으로 남깁니다. 해당 실제 확인에서는 검증을 실행하지 않았습니다.
#52는 적용된 복사본을 별도 승인으로 확인하는 선택적 고정 소스 검사를 추가합니다.
해당 소스 전용 모드에서 런타임 검증은 `not-run`이며 새로운 실제 모델 근거를 제공하지 않습니다.
#54는 정확한 내장 설정·health fixture의 별도 opt-in [런타임 계획](../guides/RUNTIME_VERIFICATION.md)을
추가합니다. 임의 소스나 인가 테스트가 아닙니다. #54에서 별도로 승인한 소스 실제 연동의
초안·적용·런타임·복구 확인 1회가 통과했습니다. alpha.3의 독립적으로 확인한 공개 산출물에는 별도
패키징 근거가 있으며 해당 실제 실행의 범위를 넓히거나 더 넓은 #35 전체를 완료하지 않습니다.
`scan`은 대상 애플리케이션이나 Codex를 실행하지 않습니다.
명시적으로 실행한 `doctor`는 진단을 위해 설치된 Codex CLI를 호출할 수 있습니다.

- [x] 같은 경로의 반복 mount를 포함해 라우트 등록에 구별되는 안정적 식별자와 원본 handler·app·include

라우트 직접 선언(#28)과 상속 등록 맥락(#29)은 alpha.2에 포함되고 alpha.3에도 유지합니다.
오프라인 AI 계약(#33)은 공개된 제한적 fixture 흐름의 기반이며 더 넓은 #35 작업은 남아 있습니다. 모든 Python 구문 지원이나
런타임 등록 여부를 확정한다고 주장하지 않습니다.

## 단계 1 — 의존성 근거 수집

1. [x] 라우트에 직접 선언된 의존성을 수집합니다 ([#28](https://github.com/casing1/authzest/issues/28)).
       매개변수 기본값, 지원하는 인라인 `Annotated`, 데코레이터의 `dependencies`가 대상입니다.
       실제 `Depends`·`Security` import, 별칭과 이름 가림을 구분하고 종류, 대상, 소스 위치,
       선언 위치 종류, 해석 상태와 정적으로 확인한 scopes를 기록합니다.
       `reference`는 단순/점 연결 이름 구문을 뜻하며 callable·import 해석 성공이나 보호 여부가 아닙니다.
2. [x] app/router/`include_router` 근거를 각 라우트 등록에 연결하고 반복 등록별 맥락을 보존합니다
       ([#29](https://github.com/casing1/authzest/issues/29)). #32의 등록 식별자를 사용하며 경로나 handler만으로
       묶지 않고 반복 mount별 맥락을 구분합니다.
       라우트 직접 `dependencies`를 유지하고 합친 소스 맥락을 `effective_dependencies`로 제공하며
       런타임 실행 순서나 인가 판정으로 표현하지 않습니다.
3. [ ] 문서화한 범위의 의존성 참조와 중첩 의존성 관계를 해석합니다.
       누락·순환·동적·override·미지원 관계는 추측하지 않고 명시적으로 남깁니다.
4. [ ] 근거가 없다는 사실을 부정적인 보안 판정으로 바꾸지 않도록 미해석 근거와 분석 한계를
       리포트에 드러냅니다.

완료 조건: 지원하는 로컬 fixture에서 예상한 선언 근거와 원본 소스 위치가 CLI/API 리포트에
나타납니다. 기존 route 필드는 호환성을 유지하거나 의도한 스키마 변경을 문서화합니다.
각 이슈에는 검출·일반 비보안 의존성·미해석 사례가 포함되며 대상 소스를 실행하지 않습니다.

## 단계 2 — 해석 기준과 리포트 계약

- [ ] 인증(호출자가 누구인지)과 인가(무엇에 접근할 수 있는지)를 구분합니다.
- [ ] 분류 이름을 정하기 전에 지원하는 근거 규칙, 명시적 공개 endpoint, 미지원 middleware,
      override, 사용자 정의 검사와 객체 단위 정책을 정의합니다.
- [ ] 관찰된 선언을 인증 근거·인가 근거·알 수 없음/불완전 분석과 분리합니다.
      `Depends` 또는 `Security`만으로 보호를 보장하지 않습니다.
- [ ] 선행 리포트 계약을 정책 근거와 향후 finding에 맞춰 확장하고 결정론적 순서·소스 경로 처리·텍스트/JSON
      호환성을 유지합니다.
- [ ] 향후 finding을 도입할 때 선행 CLI 종료 계약을 확장합니다.
      스캔 성공이나 라우트 0개를 보안 통과라고 설명하면 안 됩니다.
- [ ] 예상 정책 표시와 예상 결과를 갖춘 작은 로컬 fixture 모음을 유지합니다.
      공개 endpoint, 일반 DI, 인증 검사, 역할/소유권 시나리오와 미해석 사례를 포함합니다.

완료 조건: 검토자가 소스 근거와 문서화한 규칙으로 모든 보고 상태를 설명할 수 있습니다.
fixture 평가에서 일치·오탐·미탐·unknown 사례를 기록하고, 지원하지 않는 애플리케이션 동작을
조용히 안전하거나 취약하다고 선언하지 않습니다.

현재 [리포트 계약](../reference/REPORT_CONTRACT.md)은 부분 분석이어도 리포트를 반환하면 기본 종료 코드 0을
유지합니다. opt-in `--strict`는 확인한 부분 분석에 1을 반환하고 잘못된 저장소 입력에는 2를 반환합니다.
구조화된 진단은 일부 미해석 사례와 소스/읽기 오류를 기록하며 모든 미지원 선언을 포괄하지 않습니다.
`bounded` 상태나 종료 코드 0은 완전한 분석 또는 보안 통과를 뜻하지 않습니다.

## 단계 3 — 설명 가능한 결정론적 검사

- [ ] 문서화하거나 사용자가 선언한 접근통제 기대 조건을 대상으로 범위가 좁은 소스 검사를
      추가합니다. 인식 가능한 의존성이 없다는 사실만으로 취약점이라고 하지 않습니다.
- [ ] 소스 근거를 연결하고 심각도·확신도·분석 완전성을 구분합니다.
- [ ] 기존 JSON 리포트 위에 사유가 있는 suppression, 회귀 사례와 안정적인 finding 내보내기를 추가합니다.
- [ ] finding 검토 방법과 도구가 증명하지 못하는 범위를 적습니다. 일반적인 런타임 인가 정확성이나
      객체 소유권 보장도 그 한계에 포함됩니다.

완료 조건: 모든 규칙에 검출·비검출·미해석 fixture와 AI 없이 검토할 수 있는 설명이 있습니다.
검사는 로컬 소스를 대상으로 하며 취약점 악용 절차를 생성하거나 실행하지 않습니다.

## 단계 4 — Codex 보조·사용자 승인형 개선

근거/리포트 계약과 초기 의존성 fixture 다음에 진행할 최종 데모 목표입니다. 규칙을 늘리거나
두 번째 연동을 추가하기 전에 제한된 전체 흐름을 구현합니다.
[#33](https://github.com/casing1/authzest/issues/33)의 오프라인 계약과 mock은 계속 선행 조건이며,
[#35](https://github.com/casing1/authzest/issues/35)에서 제한된 Codex 제안·승인·적용·검증 흐름을
추적합니다. 오프라인 단계와 범위를 좁힌 #50 adapter만으로 완료하지 않습니다.
#50의 한 소유 fixture 실제 초안·적용·복구 확인 1회는 성공했습니다. #52 소스 설정 검사로
런타임 검증까지 완료되는 것은 아닙니다. #54의 정확한 설정·health fixture에서는 별도 승인한
소스 실제 연동의 런타임 완료 조건을 충족했고 이후 alpha.3의 별도 패키지·발행 검사도 통과했습니다.
더 넓은 제안 범위, 생성 회귀 테스트 초안과 완전한 #35 완료 조건은 별도 작업입니다.

- [x] 근거에 연결된 설명과 오프라인 평가를 정의합니다
      ([#33](https://github.com/casing1/authzest/issues/33)). 최소 불변 요청, 엄격한 응답/참조 검증,
      mock 실행 주기 테스트와 고정된 세 모드 평가 기반을 구현했습니다. 정책 기준은 관리자 승인,
      정답은 assistant 작성/코드 대조이며 mock 점수는 실제 모델 성능을 입증하지 않습니다.
- [x] 오프라인 제안/결정 단계([#46](https://github.com/casing1/authzest/issues/46))를 구현합니다.
      정확한 내용의 diff 미리보기, 연결된 명시적 결정, 만료·제공된 변경 상태를 검사합니다.
      [계약](../reference/PROPOSAL_CONTRACT.md)은 파일 적용·검사 실행·동의 신원 인증을 하지 않습니다.
- [x] [#48 소유 fixture 복사본 적용](../guides/FIXTURE_APPLICATION.md)을 추가합니다. 명시적 터미널
      결정·현재 세션의 결정 소비·POSIX 파일/상태 검사·원자적 단일 파일 교체·기록 보존·별도 확인한 복구를
      제공합니다. 기존 checkout과 검증 실행은 건드리지 않습니다.
- [x] [#50 고정 fixture 공유·adapter 경계](../guides/CODEX_FIXTURE.md)를 검증합니다. 정확한 요청 승인,
      최소 입력, timeout/취소와 별도의 복사본 적용 결정이 대상입니다.
      더 넓은 입력 공유와 검증 허가는 별도의 설계·완료 근거가 필요합니다.
- [x] 선택한 버전 고정 Codex App Server adapter로 한 소유 fixture의 실제 초안·적용·복구 확인 1회를
      완료합니다. 승인 문구는 사용자 허가 아래 assistant가 입력했으며 독립적인 사람 검토는 아닙니다.
      제한된 fixture 명령의 AI 제안은 정적 리포트와 분리하며 해당 #50 단계에서는 두 번째 transport나
      검증 실행기를 추가하지 않았습니다.
- [x] #52의 선택적 소스 설정 검사를 오프라인에서 검증합니다. 별도의 정확한 계획 결정, 소스 해시를 고정한 AST 설정 검사
      자식 프로세스, 출력·시간 제한, 명확한 건너뛰기·실패 기록과 별도로 제공하는 복구가 대상입니다.
      대상 실행이나 런타임·보안 수정 효과 검증이 아닙니다.
- [ ] 격리된 임시 workspace에서 근거에 연결된 설명, 방어적 회귀 테스트 초안과 검토 가능한 diff를 만듭니다.
      제안 중에는 스캔한 소스를 실행하거나 사용자의 worktree를 수정하지 않습니다.
- [ ] 이유, 대상 파일, 정확한 diff, 소스 revision/내용 식별값과 검증 계획을 제시합니다.
      승인은 해당 제안에만 연결하고 거절/취소 시 변경하지 않으며 입력이 바뀌면 승인을 무효화합니다.
- [ ] 적용 전 조건을 다시 확인한 뒤 승인된 diff만 적용합니다. 기존 사용자 변경을 보존하고 전후 내용 식별값을
      기록하며 관련 없는 작업을 초기화하지 않고 변경을 복구할 수 있게 합니다.
- [x] 정확한 관리 대상 설정·health fixture에 한정한 별도 승인 런타임 계획을 구현·검증했습니다(#54).
      소스 실제 연동의 초안·적용·런타임·복구 1회를 포함하며 소스 모드는 기본값을 유지합니다.
      고정 검사·종료 상태·결과·실패를 기록합니다.
      패치 적용이나 테스트 통과만으로 일반적인 인가 정확성을 증명하지
      않으며 실패했거나 실행하지 않은 검증을 성공한 수정으로 표시하지 않습니다.
- [ ] 고정한 사람의 정책 label fixture로 정적 전용·모델 단독·근거 보조 모델을 비교합니다.
      [모델 전략](MODEL_STRATEGY.md)에 따라 별도 평가 사례·반복 실행·실제 사용량·한계를 기록합니다.

완료 조건: 유지하는 fixture 하나에서 근거 → Codex 검토/제안 → 승인 또는 거절 → 승인된 패치 →
별도 승인된 검증 → 변경/결과 기록을 시연합니다. 잘못된 인용, 제공자 실패, 변경된 소스·diff,
기존 사용자 변경, 거절·취소, 검증 실패와 복구 충돌을 테스트합니다.
기본 스캔과 CI는 오프라인이며 자격 증명이 필요하지 않습니다. Codex 설정에 따라 발생하는 도구 승인을
AuthZest의 정확한 제안별 승인 단계 대신 사용하지 않습니다.

## 실행 범위와 의도적으로 제외하는 사항

단계 4의 제한된 검증은 핵심 데모에 포함되지만 `scan`의 암묵적인 일부나 임의 저장소 실행 허가는
아닙니다. 직접 소유·관리하는 fixture와 검토한 방어적 회귀 계획만 대상으로 시작합니다.
명시적 입출력 범위, timeout과 의도하지 않은 데이터 변경 방지를 갖춘 격리 환경을 사용하며
테스트 초안은 검토 전까지 신뢰하지 않습니다.

인터넷 대상 스캔, 취약점 악용 PoC 생성·실행, 자율 공격 흐름과 임의 저장소 실행은 범위 밖입니다.
더 넓은 런타임 지원이나 추가 실행 환경은 별도 설계 이슈가 필요하며 7주 결과물의 조건이 아닙니다.
