## 기존의 공백과 최소 지원 입력

현재 추천 검증기는 등록된 before 후보와 쌍에 대해서만 `registered-change`를 허용하며,
`no-change`와 `unknown`도 정상 결과입니다. 미리보기는 출력 데이터입니다.
[현재 검사기](../../../../src/authzest/runner/owner_policy_repair_check.py)는 후보 이름을 받고,
[worker](../../../../src/authzest/runner/_owner_policy_repair_worker.py)는 내장 상수를 컴파일합니다.
그 after 대조군으로는 적용된 파일의 내용이나 실제로 실행한 바이트를 입증할 수 없습니다.

변경하지 않은 `synthetic-owner-omission-v1` 쌍, 호스트가 도출한 단일 파일 diff,
[쌍 레지스트리](../reference/OWNER_POLICY_REPAIR_PAIR.md)의 검토된 사례 8개만 사용합니다.
모델 설명문과 호출자 모두 소스 파일·대체 내용·명령·실행 파일·사례·예상 정답을 선택할 수 없습니다.

- Before SHA-256: `54f36634f471d9f603218aafb379ac1d082c38e94b08284549d0311e910cf950`.
- After SHA-256: `faf39b33515a658e92e61a51c69e1a437eb3dc0dcf8511ef806558d30ee36f04`.
- 사례 SHA-256: `96f3c7bc3f88c0edc617ed64f047fbfeb95973c36cad100b49534a8f8bfadfa3`.

복사해 둔 해시, 생성된 dataclass, 미리보기 JSON 객체를 신뢰하지 말고 전체 등록 정보·검토 연결·요청·
추천을 재구성하고 검증합니다. 데이터가 유효하다고 제공자 출처가 인증되는 것은 아닙니다.
호출자 제공 데이터라는 출처 정보와 별도의 전송 기록을 보존하며, 과거 결과를 가져와도 활성 세션이나
승인이 복원되지는 않습니다.

`no-change` 또는 `unknown`이면 복사본이나 쓰기 계획을 생성하지 않고 검증된 추천을 반환합니다.
`registered-change`이면 순수 적용 미리보기를 준비한 뒤 명시적인 로컬 API 작업을 통해서만
복사본을 생성합니다. 이 새 파일 흐름에서는 제공자를 호출하지 않습니다.

## 비공개 복사본과 파일 식별값

첫 구현은 POSIX의 non-frozen Python 소스 모드와 신뢰하는 로컬 운영자를 지원합니다.
새 시스템 임시 디렉터리를 `0700` 모드로 만들고, 등록된 before 바이트로 고정 `policy.py`를
`0600` 모드로 생성합니다. 고정 증거 파일 `before.txt`·`after.txt`·`record.json`을 보존합니다.
제품 API는 기존 경로·목적지 상위 디렉터리·checkout·디렉터리 트리·재개 파일을 받지 않습니다.
테스트는 비공개 주입 지점을 통해 pytest가 소유한 임시 상위 디렉터리를 넣을 수 있습니다.

전용 소유 정책 workspace/coordinator를 사용합니다.
[`FixtureWorkspace`](../../../../src/authzest/runner/_fixture_workspace.py)의 제한된 I/O 패턴을
따르되 기존 fixture의 파일명이나 검증 허용 목록을 확장하지 않습니다. 디렉터리 descriptor를
유지하고 상대 경로 작업, `O_NOFOLLOW`/`O_NONBLOCK`, 배타적 생성, 현재 사용자 소유의 일반
단일 링크 파일을 사용합니다. 작업마다 디렉터리 식별값·소유권·모드를 검사합니다. 한 번 읽는 양은
최대 32,768바이트이며 개행 정규화 없이 정확한 UTF-8 왕복 변환이 가능해야 합니다.
읽기 전후의 descriptor와 파일명에 해당하는 메타데이터인 장치·inode·모드·소유자/그룹·링크 수·
크기·mtime·ctime 및 바이트를 비교합니다. 열린 descriptor와 현재 파일명은 같은 파일을
가리켜야 합니다. 필요한 기본 기능을 지원하지 않으면 거부합니다.

적용은 현재 파일을 추적 중인 원래 snapshot과 비교하고 정확한 등록 after 바이트를 임시로 준비한 뒤,
교체 직전에 상태와 결정을 다시 검사하고 원자적 rename을 수행하여 fsync와 새 snapshot을 확인합니다.
복구도 추적 중인 적용 snapshot을 요구하며 원래 등록 before 바이트를 씁니다. 새 inode로 내용을
복원하는 것이며 원래 파일시스템 메타데이터나 기존 checkout의 rollback은 보장하지 않습니다.

완료·거절·취소·실패 후에도 복사본과 증거를 유지합니다. 세션을 닫으면 descriptor만 해제하고
복사본은 삭제하지 않습니다. 초기화 실패 시 확인된 경로와 실패 단계를 보고하며 기록이 존재한다거나
쓰기가 되돌려졌다고 주장하지 않습니다. 원자적 rename은 악의적으로 동시에 쓰는 동일 사용자에 대한
compare-and-swap이 아닙니다. 운영자는 동시 수정을 피해야 하며, 이는 OS sandbox나 다중 파일
트랜잭션이 아닙니다.

## 계획과 별도의 활성 결정

제안된 API 이름은 경계를 설명하며 현재 호출 가능한 인터페이스가 아닙니다.

- 순수 적용 준비기는 요청·추천을 재검증하고 등록된 diff를 만듭니다.
- `OwnerPolicyRepairFileSession`은 처음에는 I/O를 하지 않으며 명시적 복사본 생성으로 활성 세션을 시작합니다.
- 단계별 미리보기·결정·작업 메서드는 before 검사, diff 수락, 적용, after 검사, 복구를 처리합니다.
  어떤 메서드도 다음 효과로 자동 진행하지 않습니다.
- 결과 검증기는 데이터 일관성만 검사하며 경로를 다시 열거나 작업에 권한을 부여할 수 없습니다.

각 단계 계획은 종류·스키마·recipe, 작업, 새 세션 nonce, generation, 요청·추천 ID,
쌍·내용·검토 식별값, before/after 및 diff 해시, 고정 파일명, workspace 식별값,
정확한 현재 파일 snapshot과 관련된 이전 완료 ID를 연결합니다. 전체 미리보기는 해당 작업과
관련된 소스·diff, 범위, 사례, 예상 정답, worker 바이트와 제한을 표시합니다.
해시만으로는 충분히 내용을 파악한 결정을 내릴 수 없습니다. 모델·검토자의 설명문은 자식 입력에
포함하지 않습니다.

diff 수락은 호스트가 도출한 정확한 변경에 동의했다는 기록이며 적용은 아닙니다.
적용에는 그 수락과 현재 before snapshot에 연결된 또 다른 선택이 필요합니다. 복사본 생성,
소스 공유, 사례 정답 출처 정보는 두 선택 중 어느 것도 대신하지 못합니다.
각 검사와 복구에도 자체 계획과 선택이 필요합니다.

선택 상태는 `pending`·`approved`·`declined`·`cancelled`이며 현재 단계와 정확한 계획에 연결합니다.
활성 pending 선택만 종결 상태로 바꿀 수 있습니다. 유한한 단조 시계와 최대 300초 유효 기간을
사용하며 시계 역행·오래된 ID·내용 변경·잘못된 단계/세션·가져온 결정을 거부합니다.
실패한 사전 검사를 포함하여 첫 await 또는 효과 전에 각 시도를 소비합니다.
단계마다 시도는 한 번이며 자동 재시도나 거절·취소·만료된 단계의 재개는 없습니다.
같은 복사본에서 감지한 사용자 수정은 새 승인으로도 허용할 수 없으며 확인할 수 있게 보존합니다.
이는 로컬 흐름의 gate이며 인증된 사람의 서명이나 호출자 자체에 대한 방어가 아닙니다.

## 파일 검사는 캡처한 바이트를 실행

별도의 파일 검사 종류·프로토콜·recipe·고정 worker 식별값을 도입합니다. #80, #110의
내장 worker·결과, 기존 Codex fixture 흐름은 변경하지 않습니다. 기존 범용 실행 helper가
임의 소스·경로·명령·환경을 받도록 확장하지 않습니다.

1. 활성 세션의 `policy.py`를 안전하게 읽어 계획을 준비합니다. 정확한 불변 UTF-8 바이트 snapshot,
   그 식별값·길이·해시, 후보, 등록된 쌍, 입력/예상 정답 8개, worker 바이트·해시,
   대응 규칙과 전송 recipe를 포함합니다. before에는 추적 중인 before snapshot,
   after에는 확인된 적용 snapshot이 필요합니다.
2. 새 검사 승인 후 전체 등록 정보·계획을 재검증하고 실행 직전에 파일을 다시 읽습니다.
   바이트와 추적 중인 전체 식별값이 미리보기와 일치해야 합니다. worker는 캡처한 소스 텍스트와
   입력 사례만 받고 파일시스템 경로나 예상 정답은 받지 않습니다.
3. 새 엄격한 worker는 폐쇄된 필드 집합, 중복 키·깊이·노드 수·크기 제한, 고정 등록 정보에
   대한 정확한 후보 바이트·해시와 등록된 입력 8개 전체를 검증합니다. 그 뒤에만 대체 내장 정책이
   아닌 **전달받은 캡처 소스 자체**를 컴파일합니다. 검토된 데이터를 고정 nullable dataclass에
   대응시키고 연결 식별값과 함께 정확히 8개의 boolean 관찰을 반환합니다.
4. 호스트는 전체 출력·식별값·종료·정리를 검사하고 완료 후 파일을 다시 읽습니다.
   파일이 여전히 계획한 snapshot과 일치하고 자식 및 임시 worker 디렉터리 정리가 모두 확인될 때만
   수용된 관찰을 제공합니다. 파일이 바뀌었거나 응답이 불완전하면 비교는 결론을 내리지 못한 상태로
   유지하며, 원시 worker 진단을 수용된 파일 검사 결과로 보지 않습니다.

고정 worker 텍스트, 비어 있는 비공개 worker cwd, 기존 최소 환경 패턴으로 신뢰하는
`sys.executable -I -S -c`를 실행합니다. 제안하는 제한은 입력 256 KiB, 출력 16 KiB,
깊이 32, 노드 8,192개, 사례 8개, 식별자 128자, scope 16개, 시도 1회,
프로세스 시작·입출력·완료 합계 5초와 자식 정리 추가 1초를 유지합니다. 보존하는 정책 복사본은
삭제할 임시 worker 디렉터리와 별개입니다. 네트워크·설치·모델·FastAPI·HTTP 작업은 이 recipe에
포함되지 않습니다. 이 제한은 파일시스템 호출·CPU·메모리·OS/네트워크 접근의 강제 상한이 아닙니다.
어떠한 실제 실행 승인 전에도 구현된 소스에서 실제 worker 해시를 고정해야 합니다.

## 상태·비교·복구

정상 파일 상태는 `ready-before`·`applied-after`·`restored-before`입니다.
결정·검사 결과·정리·증거 저장은 하나의 전역 성공 표식이 아닌 별도 필드입니다.

| 단계        | 전제 조건과 효과                                         | 거절 또는 실패                                                         |
| ----------- | -------------------------------------------------------- | ---------------------------------------------------------------------- |
| Before 검사 | 새 복사본; 승인받은 캡처 before 실행 1회                 | 복사본 유지; 기준 관찰이 없거나 유효하지 않으면 적용하지 않음          |
| Diff 수락   | 유효하게 완료된 기준 관찰; 정확한 diff만 수락            | 복사본을 유지하고 변경 경로 종료                                       |
| 적용        | 별도 선택; 추적 중인 before snapshot이 변경되지 않음     | 현재 파일 보존; 쓰기 전 실패와 반영 여부가 불확실한 쓰기를 구분        |
| After 검사  | 확인된 적용 snapshot; 별도 선택·실행 1회                 | 적용 이력 유지; 증거 저장이 확인되는 동안 별도 승인한 안전한 복구 허용 |
| 복구        | 별도 선택; 추적 중인 정확한 after snapshot이 여전히 존재 | 복사본·사용자 수정 유지; 변경됐거나 확인되지 않은 상태는 덮어쓰지 않음 |

완전한 기준 관찰도 정상적으로 불일치를 보고할 수 있습니다. 의도적으로 잘못된 before 정책은
정답 2개와 불일치할 것으로 예상합니다. 유효한 불일치 관찰은 전송 실패가 아닙니다.
등록된 after는 정답 8개와 일치할 것으로 예상하며, 이는 향후 파일 실행에 대한 예상이지
새 근거가 아닙니다. 이전 내장 대조군 관찰은 별도의 과거 기록으로 유지합니다.

같은 세션에서 수용된 before/after 관찰 중 동일한 사례·검토된 예상값·쌍·diff·worker/대응
recipe를 사용하고 각각 추적 중인 before/적용 상태에 연결된 관찰만 비교합니다.
사례별 예상값·관찰값·변화를 유지합니다. 누락·거절·만료·미확인 단계와 실행·프로토콜·정리 실패는
`not-evaluated` 또는 `inconclusive`이며 거절 관찰을 만들어 내거나 비교를 통과로 바꾸지 않습니다.
수용된 사례 불일치는 예상값 비교의 실패로 유지하며 before/after 비교에 참여할 수 있습니다.
이는 실행 실패가 아닙니다. 추적 중인 적용 상태와 증거 저장이 계속 확인된다면 after 검사
거절·실패가 복구를 막아서는 안 됩니다. 세션 수준의 증거 실패는 이 복구 경로보다 우선합니다.

적용·실행·비교·복구·파일 연결·결정 소비·증거 저장을 각각 기록합니다.
`authorization_status="unknown"`, 현재 단계의 `provider_calls=0`, 인증되지 않은 출처 정보를
유지합니다. 검사 통과는 기록된 시점의 캡처한 소유 파일 바이트를 설명하며 endpoint 강제 집행이나
현재 파일이 계속 올바르다는 보장이 아닙니다.

파일 교체와 증거 기록은 하나의 트랜잭션이 아닙니다. rename 후 실패하면 반영됨/미확인 결과와
보존된 위치를 보고해야 하며 `not-applied`나 조용한 성공으로 표시해서는 안 됩니다.
추적 중인 적용 snapshot을 확인하지 못했다면 새 승인에 따른 복구를 포함한 후속 검사와 프로그램을
통한 복구를 모두 막습니다. 복사본은 수동 점검을 위해 보존하며 재개하거나 외부 기록을 가져와
재사용할 수 없습니다. 그 snapshot과 증거 저장이 확인됐다면 검사 실패 후에도 새 복구 결정을
받을 수 있습니다. 증거 쓰기 실패는 이 복구 경로보다 우선하며 후속 효과를 차단하고 저장 실패를
보고합니다. 자동 rollback·재시도·프로세스
재시작/재개·삭제는 제공하지 않습니다. 감지한 수정, inode·링크·권한·루트 변경과 파일 누락은
관련 결정을 무효화하며 덮어쓰지 않고 보존합니다.

## 구현과 인수 검증 단계

1. 새 데이터 검증, 활성 결정, 비공개 복사본 적용·복구를 임시 파일 테스트와 함께 구현합니다.
   캡처 파일 계획과 엄격한 worker 프로토콜을 추가하고 정책을 컴파일하지 않는 소스 데이터·AST
   guard 테스트를 수행합니다. 오프라인 테스트에서는 제공자와 실제 subprocess 진입점을
   호출하면 실패하도록 패치합니다.
2. 모의 subprocess를 사용하는 제한된 전송·coordinator 테스트를 추가합니다. 전달받은 정확한
   소스를 컴파일하는 구조, 잘못되거나 부분적인 출력, 취소, 정리 불확실성, 만료·재사용,
   다른 세션·단계, 바이트가 같은 inode 교체, 읽기·임시 쓰기 도중 수정, symlink/hardlink,
   파일 누락, 권한·루트 교체, 반영·fsync·기록 실패, after 검사 거절 후 안전한 복구를 다룹니다.
   기존 #80/#110 및 fixture 회귀 검사는 허용 목록을 약화하지 않고 유지합니다.
3. 소스 검토 후 구체적인 소스·worker 해시와 새 활성 계획에 대해 제한된 실제 인수 검증을
   요청합니다. before/after worker 실행, 정확한 diff 수락, 적용, 복구는 각각 다른 결정입니다.
   이전 실행·리뷰 승인은 재사용할 수 없습니다. 과거 기록을 다시 쓰지 않고 새 근거를 기록합니다.
4. #82에서 전체 미리보기, 텍스트/JSON 출력 스트림 규칙, 거절·복구 시나리오를 갖춘 읽기 쉬운
   CLI를 연결합니다. #81/#82/#35 완료 전에는 이후의 통합 인수 검증이 필요합니다.
   GUI, 임의 저장소·AI 생성 코드 실행, 기존 checkout 수정, Windows/frozen 실행과 더 넓은
   수정 흐름은 이 첫 파일 흐름에 포함되지 않습니다. 릴리스 작업은 계속 #83에서 다룹니다.
