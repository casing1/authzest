## 상태와 요청하는 결정

아래 과거 설계 본문은 보존합니다. 이후 관리자는
[이 설계와 오프라인 구현을 승인했습니다](https://github.com/casing1/authzest/pull/110#issuecomment-6459020000).
PR #110의 소스 API와 `510377c`의 최초 오프라인/mock 근거는
[구현 참조](../reference/OWNER_POLICY_REPAIR_CHECK.md)를 확인하세요. 설계 결정은 실제 worker
실행 승인이 아니었습니다. 이후 [별도 before 전용 승인](https://github.com/casing1/authzest/pull/110#issuecomment-6460245210)은
참조 문서에 기록한 2026-10-28 11:49:55 KST before 실행으로 소비됐습니다. 예상한 두 불일치,
실행 완료, 종료 `0`, 정리 확인입니다. 이후
[별도 승인한 after 전용 실행](https://github.com/casing1/authzest/pull/110#issuecomment-6460474112)은
문서 전용 커밋 `7f9c5ce`에서 같은 런타임 코드로 2026-10-28 13:11:38 KST에 사례 8개 일치·
종료 `0`·정리 확인을 기록했습니다. 두 실행 승인은 모두 소비됐습니다. 최종 head 리뷰/전달에는
새 승인이 필요하고 파일 식별값 연결 적용/검증/복구는 별도 설계입니다. 아래 원래 제안/체크리스트는
과거 내용으로 보존하며 현재 실행 증표가 아닙니다.

**제안만 작성 — 2026-10-28 KST.** 기준 main은
`cc644a16fb67d1a89538c5b4b27549ee1f136604`입니다. 이 문서는 worker·실행 API·CLI·정책 관찰·적용·복구
기능을 추가하지 않습니다. #80을 변경하거나 새 정책 바이트·사례·예상값을 등록하지 않습니다.
문서 검사 통과는 설계 승인이 아닙니다.

[별도 실제 추천 시도](https://github.com/casing1/authzest/issues/81#issuecomment-6458726176)는 등록된
수정 쌍을 선택했지만 공유 승인은 소진됐으며 실행 권한이 아닙니다.
[기존 수정 쌍 설계](OWNER_POLICY_REPAIR_PAIR_DESIGN.md)는 실행 기능 확장 전에 별도의 고정 검사
recipe 검토를 요구합니다.

관리자에게 요청하는 결정은 **후보 하나만 다루는 전용 소스 모드 고정 검사 설계**를 먼저
오프라인·모의 프로세스 테스트로 구현할지 여부입니다. 설계 승인은 실제 정책 실행·소스 공유·자동
PR 리뷰·병합·패치·릴리스를 승인하지 않습니다. 설계 PR을 따로 병합할 의무는 없지만 worker
구현 전 정확한 설계 검토는 필요합니다. 이후 실제 worker 테스트/인수 검증은 구현된
소스·worker 식별자를 대상으로 별도 한정 결정을 받아야 합니다. #81/#35는 미완료입니다.

## 정확한 기존 입력만 사용

변경하지 않은 `synthetic-owner-omission-v1` 등록 쌍과 검토된 예상값 8개를
[수정 쌍 API](../reference/OWNER_POLICY_REPAIR_PAIR.md) 및
[등록 소스](../../../../src/authzest/codex/owner_policy_repair_pair.py)에서 사용합니다.
before는 의도적 오류를 넣은 테스트 전용 텍스트이지 생산 코드 취약점이 아닙니다. 유지 중인
올바른 정책은 after 대조군입니다. `policy.py`는 호출자 경로가 아닌 표시 이름입니다.

| 연결 대상                | SHA-256                                                            |
| ------------------------ | ------------------------------------------------------------------ |
| before 소스              | `54f36634f471d9f603218aafb379ac1d082c38e94b08284549d0311e910cf950` |
| after 소스               | `faf39b33515a658e92e61a51c69e1a437eb3dc0dcf8511ef806558d30ee36f04` |
| 예상값을 포함한 사례 8개 | `96f3c7bc3f88c0edc617ed64f047fbfeb95973c36cad100b49534a8f8bfadfa3` |
| 수정 쌍 전체 내용        | `2cbbc004b46ac2bc65b98c3e3b4b3e1e5919dd3d1b35920871372432c23203fb` |
| 기록된 예상값 검토       | `3540dd3578ee838b1bfb34f3c02019286716b47664ec942da46e8dac25d4b7e8` |

예상값은 허용 1개(`owner-control`)와 거절 7개입니다. 정적 추론으로는 before에서
`non-owner`·`exact-owner-no-normalization` 2개 불일치, after에서 8개 일치를 예상합니다.
여전히 **관찰 결과가 아닌 예측**입니다. 마지막 사례의 선행 공백을 포함해 식별자를 그대로
보존합니다. 입력 scope 목록은 고정 dataclass의 `frozenset`에만 대응합니다.
신뢰하는 신원·인증·scope·소유권 문맥은 호출자가 제공해야 합니다. 이 합성 predicate는 문맥을
인증하거나 HTTP/DB/endpoint의 접근통제를 입증하지 않습니다.

## 제안하는 모듈과 API 경계

다음 이름은 제안이며 사용 가능한 명령이나 구현 API가 아닙니다.

| 구성요소                                   | 책임                                                                   |
| ------------------------------------------ | ---------------------------------------------------------------------- |
| 기존 `codex/owner_policy_repair_pair.py`   | 변경 없는 단일 등록 기준과 정확한 수정 쌍/검토 검증                    |
| 새 `runner/owner_policy_repair_check.py`   | 전체 오프라인 계획, 1회용 세션, 최종·만료 결정, 제한된 전송·출력 검증  |
| 새 `runner/_owner_policy_repair_worker.py` | 두 등록 소스와 정확한 입력 사례 8개만 내장하는 전용 신뢰 stdlib worker |
| 후속 적용 coordinator                      | 파일에 연결된 apply/check/restore의 별도 미래 설계; 이번 단계에서 제외 |

초기 공개 API는 소스 모드 전용 `prepare_owner_policy_repair_check(candidate)`와
`OwnerPolicyRepairCheckSession(candidate)`입니다. 후보는 정확히 `before` 또는 `after`이며
묵시적인 기본값은 없습니다. `both` 선택·before 다음 자동 after 실행·경로·임의 소스·사례 대체·
실행 callback·명령·모델 응답·가져온 승인 매개변수는 없습니다.
준비와 직렬화는 자식 프로세스를 시작하거나 정책을 컴파일/평가하지 않습니다.

`owner_policy_check.py`·`_owner_policy_worker.py`, 해당 hash·recipe·#80 과거 기록은 그대로
유지합니다. 소스 monkeypatch, 허용 목록 확대, 설정 가능한 범용 executor로 바꾸는 것은
금지합니다. 새 검사기만 정확히 등록된 before 소스를 선택할 수 있습니다.
초기 단계에는 CLI나 frozen/Windows 지원을 추가하지 않습니다.

## 전체 계획과 식별자

불변·재검증 계획 하나는 후보 하나와 등록 수정 쌍/검토 기록 전체, 선택한 소스 전문/hash,
순서가 고정된 사례 8개/예상값과 hash를 연결합니다. 전용 worker 소스/hash, 버전이 있는
coordinator recipe, mapping·전송 프로토콜·비교 규칙, 고정 환경·전송 제한·정리 정책도 연결합니다.

제안 식별자는 #80과 분리한 `owned-owner-repair-check-v1`, recipe 버전 `1.0`입니다.
정확한 worker 바이트/hash와 구현 revision은 **아직 없습니다**. 실행 요청 전 구현 검토에서
이를 기록해야 합니다. 실제 내장 worker 바이트를 hash하고 호출자가 준 값이 아닌 구현에서
고정한 digest와 재검증합니다. recipe/버전과 worker 식별자는 변경 감지이며 독립 코드 인증은 아닙니다.

계획 ID는 자기 자신의 파생 ID를 제외한 버전별 전체 binding을 hash합니다. 자기 참조를 피하기
위해 이후 worker 입력에 그 ID를 추가합니다. 실행 시 전체 현재 계획을 다시 구성하고
세션에서 준비한 계획과 바이트 단위로 대조합니다. 후보·쌍·예상값·검토 기록·worker·recipe가
바뀌면 새 세션과 결정이 필요합니다.

## 별도의 1회용 결정

역직렬화 JSON이 아닌 살아 있는 세션이 실행 결정을 소유합니다. 새 전체 계획 미리보기는 선택한
소스·사례·recipe·제한을 검토할 수 있어야 합니다. 소스 API는
`decide(choice, plan_id=..., lifetime_seconds=...)`를 받으며 선택은 pending·approved·declined·
cancelled입니다. 유효 기간은 boolean이 아닌 유한한 정수/실수로
`0 < lifetime_seconds <= 300`이어야 합니다. monotonic 시각과 계산한 만료 시각은 유한한
음이 아닌 숫자여야 하며 시계 역행은 잘못된 값입니다. 잘못된 최초 결정이나 결정 시각은
세션을 되돌릴 수 없게 무효화합니다.

만료되지 않은 pending만 교체할 수 있습니다. 승인/거절/취소는 최종 결정입니다.
잘못되거나 만료된 결정 또는 최종 결정의 교체 시도는 그 세션을 되돌릴 수 없게 무효화합니다.
첫 await 전에 동기적으로 시도 1회를 소진하며 사전 검사 실패도 포함합니다. 동시 호출·재사용·
만료·시계 역행·변경된 계획은 자식 프로세스를 시작할 수 없습니다.
재시도·대체·자동 복구나 추천 결과로 추론한 승인은 허용하지 않습니다.

before 결정은 before만 승인하며 after는 승인하지 않습니다. after는 별도 세션과 새 현재
결정이 필요합니다. 기존 예상값 검토 기록은 인증된 실행 승인 증표가 아닙니다.
Python 프로세스나 내부 worker를 직접 제어하는 호출자는 이 프로세스 내부 동의 경계 밖입니다.

## Worker 입력과 프로세스 recipe

새 worker는 등록 소스 쌍과 정확한 입력 전용 사례를 내장합니다. stdin은 닫힌 JSON으로
스키마/검사/계획 식별자, 후보, 선택 소스·worker hash, 입력 사례 hash, 사례 ID·입력 식별자·
principal·report 데이터로만 이루어진 순서 있는 행을 받습니다.
예상값·모델 설명·검토자 문장·경로·소스 텍스트는 worker 입력이 아닙니다.
문법상 유효한 대체 입력을 포함해 모든 사례/문맥 변경을 거절해야 합니다.

전체 입력을 검증한 뒤 고정 내부 모듈에서 내장 후보 정책 하나만 컴파일합니다.
호출자는 등록된 두 후보 중 하나만 선택하며 임의 소스 바이트·import·파일 이름·표현식을
제공할 수 없습니다. stdout은 요청 식별자와
정확히 8개의 순서 있는 사례 ID/입력 hash/boolean 행을 반환합니다. coordinator는 정확한
binding과 엄격한 boolean을 검증합니다. 누락·추가·중복·순서 변경·형변환·비유한 수·
잘못되거나 부분적인 출력은 관찰값이 될 수 없습니다.

| 고정 제어          | 제안 값                                                                   |
| ------------------ | ------------------------------------------------------------------------- |
| 플랫폼             | POSIX, non-frozen Python 소스 설치                                        |
| 시작               | 신뢰 인터프리터, `-I -S -c`, 고정 내장 worker, shell 없음                 |
| 사례               | 정확히 등록된 8개; 호출자 확장 없음                                       |
| 방어적 parser 제한 | 입력 256 KiB, 출력 16 KiB, 깊이 32, 노드 8,192개                          |
| 사례 필드 제한     | scope 최대 16개, 식별자/scope 각각 최대 128자; 정확한 등록 값 일치도 필수 |
| 시작 + I/O + 완료  | 시도당 합계 5초                                                           |
| 종료/reap 정리     | 추가 1초                                                                  |
| 결정 유효 기간     | 최대 300초                                                                |
| 환경               | 고정 최소 환경; HOME/계정/제공자/proxy/Python 주입 환경 상속 없음         |
| 작업 경로          | 새 비공개 임시 폴더; 저장소 복사/import 없음                              |
| 프로세스 그룹      | 새 세션; 해당 실행의 프로세스 그룹만 정리 대상으로 사용                   |

의도적인 네트워크/제공자/FastAPI/HTTP/DB/install-hook 경로는 없습니다.
제한된 신뢰 프로세스 제어이지 **OS/네트워크 sandbox나 CPU/메모리 hard cap이 아닙니다**.
신뢰하는 인터프리터·도구·변하지 않는 등록 코드와 같은 사용자 권한의 적대적 동시 변경이
없다는 가정이 필요합니다. 이 설계가 임의 저장소나 AI 생성 코드를 안전하게 만들지는 않습니다.

## 결과·정리·비교 의미

예상값과 실제 boolean을 분리합니다. 전체 검증과 정리에 성공한 실행만 관찰 boolean을
변경하지 않은 예상값과 대조합니다. 종합 `passed`는 예상값 8개 일치,
`failed`는 하나 이상 불일치이지 worker 실패가 아닙니다. 의도적 오류가 있는 before는
정상 실행 완료와 실패한 비교 결과를 동시에 보일 것으로 예상합니다. 통과시키려고 예상값을 바꾸지 않습니다.

실패/미지원/거절 결과는 관찰 null·비교 unknown을 유지하며 거절 값을 꾸며내지 않습니다.
실행 `not-run`·`attempted`·`completed`와 비교 `not-evaluated`·`passed`·`failed`를
구분합니다. 자식과 임시 작업 폴더의 정리 상태를 따로 기록합니다. 자식이 없다고 확인한 시작
실패는 자식 정리 `not-needed`, 시작 중 존재가 불분명하거나 reap에 실패하면
`unconfirmed`입니다. 임시 폴더 정리에 실패하면 자식이 시작되지 않았더라도 전체 정리는
`unconfirmed`입니다. 두 자원 모두 정리가 불필요할 때만 전체 `not-needed`이며,
그 외에는 필요한 정리 단계가 모두 성공해야 확인으로 기록합니다.
추가 1초는 자식 kill/reap에만 적용합니다. 폴더 생성/삭제 등 host 파일시스템 작업의 실제
시간은 보장하지 않으므로 전체 합계 6초 hard cap이 아닙니다.
정리 확인에는 프로세스 그룹 종료/reap과 임시 폴더 정리가 포함됩니다.
시간 초과·취소·출력 초과·비정상 종료·식별자 불일치·
미확인 정리는 성공한 관찰을 내보내지 않습니다. 제한된 정리를 수행하면서 원래 취소를
보존하고 원시 stderr/예외 문장을 결과 데이터로 내보내지 않습니다.

모든 결과는 정확한 계획·선택 소스·사례·worker/recipe, 시도/정리 진단, 사례별 예상/관찰값을
연결합니다. 제공자 호출 0·인가 unknown·적용/복구 not-run을 유지합니다.
비교 실패는 endpoint 취약점 판정이 아닙니다.

후속 순수 비교 helper는 수정 쌍·사례/예상값·worker·recipe binding이 일치하는 별도 검증된
before/after 결과만 결합할 수 있습니다. 후보/소스/계획 ID는 의도대로 서로 다르며 명시적으로
남깁니다. 입력 역할은 before 다음 after여야 하며 바뀐 순서·오래된 값·부분 값·다른 문맥·
위조한 shape는 거절합니다. 가져온 기록은 호출자 제공 데이터이지 실행을 인증한 증거가 아닙니다.
helper는 빠진 검사를 실행하거나 패치를 적용하지 않습니다.

**내장 after 실행은 대조군 관찰이지 적용된 파일의 검증이 아닙니다.** 두 실행 모두 적용
작업 폴더를 읽거나 패치 적용 사실을 입증하지 않습니다. 새 복사본 적용에는 파일 식별자를
연결한 별도 설계와 diff/apply/check/restore 결정이 필요합니다.
이 관찰을 나중에 적용된 파일 검증으로 바꿔 표시하지 않습니다.
