## 제품 방향과 이번 버전 목표

AuthZest의 제품 방향은 FastAPI 소스 기반 인증·인가 분석과 AI 보조 패치입니다. 0.1.0은 다른 로컬
폴더에서 명시적으로 선택한 자체 완결 단일 Python 앱 파일의 **GET 객체 소유권 인가 오류**에
집중합니다. 라우트 선언만으로는 누가 무엇을 읽어야 하는지 알 수 없으므로 정책은 사용자가 제공합니다.

| 구분      | 0.1.0 필수 동작                                                                                                                                                                                                |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 소스·환경 | 선택한 FastAPI 앱 파일 하나, 메모리 데이터, 명시적 앱 진입점과 지원하는 고정 의존성을 사용합니다. 최초 활성 환경은 macOS arm64·Python 3.12 소스 설치·Docker Desktop입니다.                                     |
| 인증 경계 | 검토한 합성 또는 지정 사용자 식별 구성을 사용합니다. 정책상 필요한 익명 거부를 확인하되 로그인 체계나 실제 신원 검증을 보장하지 않습니다.                                                                      |
| AI 산출물 | 모델이 제한된 새 HTTP PoC 요청(코드가 아닌 데이터)과 교체 소스를 작성합니다. 등록된 after 템플릿 선택은 생성으로 인정하지 않습니다.                                                                            |
| 독립 검증 | 정확한 before/after 소스를 격리한 A guest에서 실행하고 신뢰한 B 관찰자로 제한된 HTTP 결과를 수집합니다. 정책 정답은 AI 출력과 독립적으로 호스트에 둡니다.                                                      |
| 수정·복구 | 정확한 diff와 현재 명시적 결정을 검토해 복사본을 적용·검증한 다음, 원본 단일 파일의 최종 적용을 별도로 승인합니다. 백업을 보존하고 바뀐 원본을 거부하며 이후 사용자 편집을 덮지 않는 검토형 복구를 지원합니다. |
| 표시      | CLI 진행 표시와 전체 결과 JSON을 제공합니다. 외부 흐름의 GUI는 저장 결과 조회로 한정하고 미지원·미실행·불명·실패·복구 상태를 표시합니다.                                                                       |

독립적으로 검토한 사례 4–8개에 지정 회귀 하나, 정상 소유자 접근, 비소유자 거부, 해당하는 익명
거부와 공개 의도 또는 검토한 비해당 사유를 포함합니다. 작성자·사용자 식별 가정·before/after
기대값을 기록합니다. 구체적 정책 정답과 이미지·런타임 입력은 실제 검증 전에 별도로 검토해야 합니다.
유한한 결과 일치는 해당 사례의 근거이며 앱 전체의 안전성 인증이 아닙니다.

## 후속으로 미루는 작업

- 범용 FastAPI 취약점 분석과 JWT·OAuth·로그인·세션·외부 신원 제공자 자체의 결함 분석.
- 다중 파일·패키지·`src` 구조, 프로젝트 의존성 설치, DB와 외부 서비스.
- 다른 HTTP 메서드, 임의 요청 스크립트, 모델이 작성한 Python·pytest PoC 실행.
- 외부 활성 GUI 조작, 추가 native·운영체제 활성 런타임, 추가 adapter와 비교 평가 확장.

기존 고정 시연, v1.0 제안 경로, v1.1 테스트 인터페이스와 T/A/B 기반은 각 한계와 함께 유지합니다.
HTTP 데이터 전용 A/B 경로에는 별도의 요청·profile·결과·조작 계약이 필요하며 이번 범위 고정에서는
구현하지 않았습니다. 기존 요청을 묵시적으로 변환하거나 T 식별자·개수·pytest 통과·실제
실행 근거를 꾸며 새 경로에 맞추지 않습니다.

## 현재 상태와 완료 조건

범위를 고정할 때 기준 `59ed05b`에는 외부 제안 입력, 비공개 파일 API, 제공 자료 비교 계약, 봉인한
입력과 미실행 guest·생성 계획 기반이 있었습니다. 저장소 이미지는 빌드 전이었고 전체 외부 조작 흐름·
최종 원본 쓰기·설치형 실제 수용은 미완료였습니다. 과거 내장 시연 근거는 새 모드의 실행 근거와 구분합니다.

**진행 상황 — 2026-11-25 KST.** PR #217–#219로 다음을 추가했습니다.

- 직접 A/B phase, `repo-fix`/`repo-restore`.
- 백업·메타데이터 보존·복구를 갖춘 원본 적용.
- runtime 설정 스크립트, 시연 앱, 저장 결과 보기.

A/B 이미지를 빌드했고 비공개 프로필을 Docker Desktop 29.9.3에서 읽기 전용으로 확인했습니다. 소스
checkout에서 `gpt-5.6-sol`이 지정 회귀와 같은 PoC와 수정을 만들었습니다. 수정 전 검사는 검토한 수정 전
응답 5/5와 일치해 결함을 재현했고 수정 후 검사는 수정 후 응답 5/5와 일치했습니다. 모든 guest를 삭제했고
백업을 남긴 채 원본에 적용했습니다. 이후 `repo-restore`는 사용자 편집을 거절했고 편집을 되돌린 뒤 원본
바이트를 복구했습니다. 적용 시점의 편집 충돌 거절은 회귀 테스트로만 확인했습니다. 시연 사례 5개는 assistant가 초안을
작성했고 2026-11-25에 유지보수자가 검토·수용했습니다.

이어서 PR #219 헤드 `c98bd59`로 만든 wheel을 새 가상환경에 설치하고 새로 복사한 시연 앱에서
site-packages의 설치본으로 실행했습니다. `gpt-5.6-sol`이 다시 지정 회귀와 같은 PoC와 소유자 확인 수정을
만들었습니다. 수정 전·후 검사가 각각 5/5 일치했고 모든 guest를 삭제한 뒤 백업과 함께 원본에
적용했으며 설치본 `repo-restore`로 복구했습니다. 저장 결과는 대시보드 뷰어에서 재구성한 diff와 함께
열렸습니다. 이후 리뷰 수정은 결과 뷰어와 그 테스트만 바꿨고 `repo-fix` 실행 코드는 그대로입니다.
