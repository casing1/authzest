# 보안 정책

## 지원 버전

AuthZest는 초기 개발 단계입니다. 최신 `0.1.x` 사전 릴리스와 기본 브랜치의 최신 커밋에 보안
수정이 제공됩니다. 이전 preview build는 지원하지 않습니다.

## 취약점 신고

공개 issue, discussion 또는 pull request에 취약점 세부사항이나 실제 대상의 민감한 소스 코드를
올리지 마세요.

이 저장소에서 GitHub private vulnerability reporting을 사용할 수 있다면 해당 채널을 이용해
주세요. 비공개 신고 채널이 보이지 않는다면 공개 메시지에 민감한 내용을 포함하지 말고, 먼저
관리자에게 비공개 연락 방법을 요청해 주세요.

가능한 범위에서 다음 정보를 포함해 주세요.

- 영향을 받는 component와 보안 영향
- 전제 조건과 재현 절차
- 제3자의 데이터를 노출하지 않는 최소 proof of concept
- 완화 방안 또는 관련 참고자료

관리자는 신고를 확인하고 영향 범위와 예상 대응 일정을 안내해야 합니다.

## 안전한 사용

AuthZest는 본인이 소유하거나 명시적으로 테스트 권한을 받은 소스 코드와 환경에서만 사용해야
합니다. 저장소에는 credential, 운영 데이터, 개인정보 또는 독점 코드가 포함될 수 있습니다.

기본 `authzest scan`은 결정론적 로컬 소스 스캔입니다. API key가 필요하지 않으며 Codex를 호출하거나
대상 애플리케이션을 실행하거나 파일을 수정하지 않습니다. `authzest doctor`를 명시적으로 실행하면
설치된 Codex CLI를 버전/로그인 진단에 사용할 수 있지만, 모델을 호출하거나 소스 공유를 승인하지는
않습니다. 진단 출력을 공유하기 전에 검토해 주세요.

별도의 opt-in POSIX `authzest codex-fixture` 흐름은 번들된 소유 fixture를 대상으로 구현되어 있습니다.
정확한 요청의 공유 승인 전에 작업/소스 payload, 호스트 지침, 출력 스키마를 미리 보여주며,
신뢰하는 로컬 Codex 설치와 기존 ChatGPT 로그인을 사용합니다. Codex는 자체 harness context를 추가합니다.
실제 흐름은 유지하는 `main.py`의 `debug=True`를 `debug=False`로 바꾸는 변경만 허용하며,
임의 저장소 경로를 받거나 기존 checkout을 수정하지 않습니다.
[Codex fixture 안내](guides/CODEX_FIXTURE.md)를 참고해 주세요.

공유, 새 비공개 복사본에 정확한 diff 적용, 검증, 복구는 각각 별도의 결정이 필요합니다.
기본 검증 계획은 소스 설정을 실행하지 않고 확인합니다. `--runtime-check` 선택은 실행 승인이 아닙니다.
별도 결정 후 고정 worker가 일치하는 번들 fixture 상수만 실행하고 debug/health 동작을 관찰할 수
있습니다. 이는 OS/네트워크 샌드박스, 인가 테스트, 보안 수정 효과의 증명이 아닙니다.
터미널 선택과 보존된 기록은 인증된 사람의 승인 영수증이 아닙니다.
[런타임 검증](guides/RUNTIME_VERIFICATION.md)을 참고해 주세요.

소스 공유 전 최소 권한, 명시적 사용자 승인, 민감정보 제거, timeout과 실패 격리 요구사항을
계속 유지합니다. 공개 번들 fixture는 임의 저장소의 일반적인 비밀정보 탐지나 제거가 구현됐다는
근거가 아닙니다. 이 실제 흐름은 일반 저장소 AI와 생성된 테스트 실행을 아직 지원하지 않습니다.
Timeout과 애플리케이션 시도 횟수 제한이 제공자 내부 재시도·토큰·금액의 강제 상한은 아니며,
누락된 사용량은 미확인으로 유지합니다.

## 위협 모델과 현재 경계

[저장소 위협 모델](reference/threat-model.md)은 확인한 소스, 보호 자산, 신뢰 경계, 가정과 검토 가설을
정리합니다. 완료된 보안 감사나 포괄적인 발견 사항 제외 목록이 아닙니다.
분석 대상 애플리케이션의 인가 정책은 별도 입력입니다.

선택적 로컬 API는 서버 시작 시 선택한 작업공간을 스캔하며 요청이 새 경로를 선택할 수 없습니다.
CLI UI의 기본값은 루프백입니다. 애플리케이션 인증이나 tenant 격리가 구현되어 있지 않으므로
공개/공유 서비스처럼 취급하지 말고 로컬에서 운영자가 통제하는 용도로 유지해 주세요.
비공개 fixture 복사본과 기록은 검토를 위해 보존합니다. 파일 상태 확인과 원자적 교체는
같은 사용자 권한의 적대적인 동시 작성자를 격리하지 않습니다.

## 보안 설계 원칙

- 네트워크 요청과 외부 프로세스 실행은 기본적으로 비활성화해야 합니다.
- 로컬 API endpoint가 호출자 제어 경로를 무제한 파일시스템 접근으로 바꾸면 안 됩니다.
- Finding에는 근거가 있어야 하며 확인, 의심, 알 수 없음 상태를 구분해야 합니다.
- 보안 통제에는 병합 전 regression test가 필요합니다.
- 비밀정보와 개인정보를 저장소에 커밋하면 안 됩니다.
