# 소유 보고서 정책의 읽기 전용 Codex 검토

[문서 목차](../INDEX.md) · [소유 보고서 정책](OWNER_POLICY.md) · [Codex 설정 fixture](CODEX_FIXTURE.md)

## 범위와 제공 상태

[#75](https://github.com/casing1/authzest/issues/75)는 현재 소스에 `codex-owner-review`를 추가합니다.
유지하는 보고서 접근 예제 하나를 opt-in 읽기 전용 Codex 검토와 구조화된 방어적 테스트 사례
초안에 연결합니다. 공개 alpha.3 바이너리에는 없습니다. 패키지 버전 `0.1.0a3`, scan report
schema `1.2`, 공개 산출물과 별도 `codex-fixture` 흐름은 그대로입니다.

이 단계에는 코드 생성·diff·패치 적용·HTTP endpoint 검사·예제 애플리케이션·endpoint·정책 함수 실행이
없습니다. 유효한 결과는 unknown을 유지하거나 근거 있는 변경이 필요 없다고 답할 수 있으며
억지로 패치를 만들지 않습니다. 일반 저장소 검토와 더 넓은
[#35 흐름](https://github.com/casing1/authzest/issues/35)은 미완료입니다.
오프라인 테스트와 미리보기는 실제 모델 인수 검증 결과가 아닙니다. 2026-09-24·2026-09-30의
실패 이후, 새로 승인받은 2026-10-01 `9257bd7` 실제 시도에서 `draft-ready`를 받았습니다.
근거 연결 답변 1개와 구조화된 사례 10개가 host 검증을 통과해 제한된 읽기 전용 제공자 인수
검증을 완료했습니다. 사례 정답 승인이나 endpoint 검사는 아닙니다. 아래에 세 시도와 한계를
기록합니다. 다음 제공자 시도에는 새로운 승인이 필요합니다.

## 공유 전에 미리보기

변경을 포함한 소스 설치본을 사용하세요. `MODEL`은 요청하려는 정확한 모델 ID로 바꿀 자리이며
모델을 자동 선택하지 않습니다. 지원 OS 어디에서든 다음 명령을 사용할 수 있습니다.

```bash
authzest codex-owner-review --model MODEL --preview-only
```

완전한 JSON 미리보기 하나를 출력한 뒤 질문·Codex 실행·계정 접근·네트워크 요청 없이 종료합니다.
Codex나 로그인도 필요하지 않습니다. `--json`·임의 경로·자동 승인 옵션은 없습니다.
미리보기에는 요청·작업 프롬프트·host 지시·출력 스키마·제한과 승인을 연결할 `sharing_id`가
포함됩니다. 이 ID는 요청 ID만이 아닌 전체 공유 내용을 식별합니다. Codex가 자체 harness 맥락을
추가하므로 미리보기가 모델의 전체 맥락을 보여준다는 뜻은 아닙니다.

작업·소스 입력은 다음으로 제한됩니다.

- 소스 식별값과 줄 참조가 있는 패키지 내 관리 snapshot
  `examples/fastapi_owner_policy/main.py`와 `policy.py`. checkout을 읽는 대신 내장 snapshot을 사용합니다.
- 명시적인 소유자 전용 보고서 정책과 신뢰 가정.
- 소스를 import·실행하지 않고 도출한 정적 라우트·`Security` 선언 근거.

개발용 28개 사례 행렬·예상 label·고정 평가 corpus는 모델 입력이 아닙니다. 테스트는 패키지
snapshot과 유지하는 예제가 같은지 확인하지만 명령 자체가 로컬 예제의 변경 여부를 확인한다고
주장하지 않습니다. 다른 저장소 파일·사용자 지정 경로·자격 증명은 작업·소스 입력에 넣지 않습니다.

## 명시적이고 제한된 계정 사용

지원 POSIX 시스템에서는 신뢰하는 Codex **0.153.0** 설치본과 Codex가 관리하는 기존 ChatGPT
로그인을 사용합니다. 이는 호환성 고정이며 현재 설치본이나 최신 Codex가 호환된다는 뜻은
아닙니다. 명령 자체가 Codex 설치·로그인·자격 증명 파일 읽기를 하지 않습니다.

```bash
authzest codex-owner-review --model MODEL --timeout-seconds 120
```

timeout 기본값은 120초이며 120초를 초과할 수 없습니다. 먼저 전체 JSON 미리보기를 표시합니다.
표시된 `share <sharing_id>` 문구를 정확하게 입력해야 제공자 경로를 허용합니다. Enter·다른 답·질문
취소는 아무것도 공유하지 않고 제공자 프로세스를 시작하지 않습니다. 미리보기·거절은 지원 OS
전체에서 가능하지만 실제 제공자 경로는 POSIX 전용입니다. 로그인 성공·정책 기준 승인·이번 기능
구현 허가는 소스 공유 동의를 대신하지 않습니다.

동의 후 공유하는 버전 고정 App Server 전송 계층은 애플리케이션이 시작하는 turn을 최대 1개만
허용하며 AuthZest 재시도·모델 fallback·대체를 하지 않습니다. Codex 내부 통신 재시도는 사용량을
소비할 수 있습니다. timeout과 애플리케이션 시도 횟수는 토큰·금액 상한을 보장하지 않으며
사용량을 모르면 unknown으로 유지합니다. 전송 계층은 [설정 fixture 안내](CODEX_FIXTURE.md)의
유효 설정·식별값·도구/맥락·프로토콜 검사를 재사용합니다. 비어 있는 작업 디렉터리에서 시작하고
ChatGPT 인증의 내장 OpenAI 제공자만 받으며 요청/협상한 모델을 확인하고 도구 작업을 거절합니다.
소스 실행·shell 명령·저장소 탐색·HTTP 테스트는 요청한 검토에 포함하지 않습니다. 신뢰하는
로컬 Codex 설치본이 전제이며 신뢰하지 않는 실행 파일의 sandbox를 보장하지 않습니다.

공식 [App Server 문서](https://learn.chatgpt.com/docs/app-server)는 기반 인터페이스를 설명합니다.
AuthZest의 정확한 공유 범위·버전 고정·읽기 전용 결과 계약은 일반 Codex 제한이 아니라 더 좁은
애플리케이션 규칙입니다.

## 민감정보를 제거한 실패 진단 — 2026-09-28 소스 추가

최종 결과에 `failure`를 추가합니다. 보고할 실패가 없으면 `null`이며, 실패하면 허용 목록의
문자열 `stage`·`code`·`turn_start`만 담는 객체입니다. 필터 없는 제공자 오류나 입증된 근본
원인이 아니라 adapter가 관찰한 로컬 실패 경계를 기록합니다. 예를 들어 `stage=turn-stream`과
`code=protocol-rejected`는 turn stream 처리 중 검사하는 프로토콜 조건이 충족되지 않았다는
뜻이며, 이것만으로 인증·quota·네트워크 실패를 단정하지 않습니다.

단계는 adapter 준비·요청 검증·시작·설정·계정/모델 확인·thread/turn 시작·turn stream 처리·
응답/결과 검증·정리를 구분합니다. 분류하지 못한 실패는 `unknown`을 사용하며 adapter가 제공한
지원하지 않거나 잘못된 형식의 진단값은 안전한 대체값으로 바꿉니다. `timeout`·`transport-error`·
`response-invalid` 같은 고정 코드는 예외 원문을 복사하지 않고 실패 유형을 구분합니다.

| `turn_start`    | 로컬 관찰                                                                    |
| --------------- | ---------------------------------------------------------------------------- |
| `not-attempted` | 로컬 `turn/start` 전송 시도가 기록되지 않았습니다.                           |
| `attempted`     | 로컬 전송을 시도했으나 일치하는 유효한 turn 시작 응답은 확인하지 못했습니다. |
| `acknowledged`  | 유효한 turn ID가 있는 일치하는 응답을 확인했습니다.                          |
| `unknown`       | 제공된 진단으로 turn 시작 상태를 확인할 수 없습니다.                         |

어느 상태도 실제 응답 모델·과금·실행·완료를 입증하지 않습니다. 기존 `application_turn_attempts`는
서버가 수용한 turn 횟수가 아닙니다. 실패 결과의 사용량·경고 횟수·재시도 횟수는 계속 `null`이며
전송 진행 상태로 추론하지 않습니다. 진단의 세 필드에는 제공자 메시지 원문·로그·예외 원문·경로·
식별값·계정 상세·모델 부분 출력을 넣지 않습니다.

진단 구현은 오프라인에서 검사했으며 [PR #76](https://github.com/casing1/authzest/pull/76)에서
추적합니다. 해당 구현 자체가 새로운 실제 모델 결과·릴리스·인수 검증 완료는 아니었습니다. 취소는 계속 전파되어
CLI 종료 코드 `130`을 유지합니다. 버전 고정·공유 내용·제한·재시도 금지 규칙은 그대로이며
진단이 제공자·소스·도구·실행 권한을 추가하지 않습니다.

## 오프라인 계약 정합성 개선 — 프롬프트 버전 2

소스 후속 작업은 거절된 제공자 출력을 보관하지 않고 고정된 검증 사유 코드를 추가합니다.
실패 객체는 계속 `stage`·`code`·`turn_start`의 정확히 세 필드만 가집니다. 분류 가능한 소유 정책
검토 검증 실패는 다음 코드 중 하나로 처음 실패한 규칙을 구분합니다.

| 코드                           | 로컬 검증 범주                              |
| ------------------------------ | ------------------------------------------- |
| `validation-json`              | JSON 해석 또는 JSON 값의 유효성             |
| `validation-budget`            | 입력 또는 결과의 제한된 크기·복잡도         |
| `validation-shape`             | 필수 객체·필드·컬렉션·타입 구조             |
| `validation-text`              | 제한된 길이의 공백 아닌 텍스트와 허용 문자  |
| `validation-duplicate`         | 중복을 허용하지 않는 식별값·참조·scope      |
| `validation-question-coverage` | 요청한 질문 집합의 누락 없는 응답           |

이 닫힌 코드 집합에는 필드값·경로·식별값·예외 원문을 넣지 않습니다. 처음 실패한 검사를
나타내며 모든 오류의 목록이나 입증된 제공자 측 원인은 아닙니다. 분류하지 못한 응답 검증
실패는 `response-invalid`를 유지하고 잘못된 adapter 진단은 계속 안전한 대체값을 사용합니다.
새 코드는 과거 두 응답을 복원하거나 거절된 초안을 수용된 결과로 바꾸지 않습니다.

소유 정책 검토 프롬프트는 이제 `owner-policy-review-v2`입니다. 출력 스키마는 중첩 `anyOf`
분기로 `hypothesis`를 공백 아닌 답변과, `unknown`을 null 답변 및 한 개 이상의 명시적 unknown과
연결합니다. 지원하는 텍스트·제어문자 제한과 근거 목록 최소 개수도 표현합니다. null을 허용하는
합성 subject/report 식별값은 부정 사례 데이터로 빈 문자열이나 공백 문자열을 계속 허용하지만
제어문자는 허용하지 않으며 유효한 신원으로 정규화하지 않습니다. 프롬프트에는 필수 소스/정책
인용과 제한된 사례 데이터 규칙을 명시합니다.

이 스키마 설계는 지원하지 않는 조건부 조합 대신 문서화된 Structured Outputs 부분집합의
중첩 `anyOf`와 지원하는 문자열/배열 제약을 사용합니다.
공식 [Structured Outputs 가이드](https://developers.openai.com/api/docs/guides/structured-outputs)를
참고하세요. 고정한 Codex `0.153.0` 전송 경로가 실제 호출에서 변경된 스키마를 수용한다는
확인은 아닙니다. host 검증은 계속 최종 기준이며 실패 시 거절합니다. 정확한 근거 포함 여부·
중복 금지·UTF-8 유효성·전체 직렬화 결과 제한은 계속 host 검사가 필요하며 제공자 스키마가
모두 표현하지는 않습니다. 오프라인 정합성 사례는 스키마가 강제하는 제약과 의도적으로 유지하는
host 전용 검사를 구분하며 JSON Schema 유효성을 정책 정답으로 취급하지 않습니다.

보수적인 정규식의 끝 앵커가 식별자 끝의 줄바꿈을 허용하더라도 host는 거절합니다.
UTF-16 엔진에서 정상적인 non-BMP 문자까지 거부하지 않도록 스키마 정규식에는 서로게이트
범위 제외를 넣지 않았으며, 단독 서로게이트는 host가 계속 거절합니다. 오프라인 일치성
검사는 실제 제공자의 스키마 엔진이 아닌 Python `jsonschema`를 사용합니다.

## 결과 해석

대화형 모드는 미리보기·동의 질문 뒤 최종 JSON 결과를 출력합니다. 전체 터미널 출력은 단일
JSON 문서가 아니며 미리보기 문서 하나만 필요하면 `--preview-only`를 사용하세요.

검증을 통과한 초안에는 근거에 연결된 검토 답변과 1–16개의 구조화된 방어적 사례가 있습니다.
각 사례는 principal/report 입력·예상 boolean·이유를 설명하며 실행 가능한 테스트 코드가 아닌
검토용 데이터입니다. host는 스키마·요청/소스 식별값·허용한 근거 참조를 확인하지만 모델의
설명이나 예상값이 옳다고 증명하지 않습니다. 결과는 `draft`, 사례 예상값은 모델 작성·미검토,
`execution_status`는 `not-run`, `authorization_status`는 `unknown`을 유지합니다.

관리자는 2026-09-24에 인증된 신원·정확한 `reports:read` scope·소유자 일치를 모두 요구하고
관리자 예외 없이 정보가 없으면 거절하는 정책 기준을 승인했습니다. assistant가 작성한 개발용
정답 label 28개나 향후 모델 작성 사례까지 독립적으로 승인한 것은 아닙니다. 예제 인증은
의도적인 미설정·기본 거절 상태를 유지합니다. 소스에 연결된 검토가 실제 인증을 구현하거나
endpoint 인가를 입증하지 않습니다.
