# 소유 fixture 복사본에 승인 후 적용

[문서 목차](../INDEX.md) · [제안 계약](../reference/PROPOSAL_CONTRACT.md)

## 범위와 지원 환경

#48은 #46 다음에 진행하는 #35의 오프라인 하위 단계입니다. 소스 checkout 데모에서 호출자가 작성한
고정 `debug=True` → `debug=False` 제안을 보여주고 명시적인 결정 후에만 적용합니다. 변경 대상은
관리하는 fixture의 **새 비공개 복사본**이며 원래 checkout은 수정하지 않습니다. AI 코드 생성·인가 테스트·
검증된 보안 수정이 아닙니다. #35의 전체 흐름은 아직 미완료입니다.

적용 도우미는 현재 지원 POSIX 파일 연산이 필요합니다. 로컬 macOS와 Linux Python CI에서 검사하며
Windows는 복사본 생성 전에 거부합니다. 기존 Windows scan/바이너리 지원은 바뀌지 않습니다.
제품 CLI/API 명령·버전·의존성·리포트 스키마·alpha.2 배포 파일도 그대로입니다.
기존 `scripts/demo_proposal.py`는 계속 파일을 적용하지 않는 모의 실행입니다.

## 대화형 데모 실행

개발 가상환경을 활성화한 소스 checkout 루트에서 실행합니다.

```bash
python -m scripts.demo_apply
python -m pytest tests/test_fixture_apply.py tests/test_fixture_apply_demo.py
```

데모는 관리하는 `tests/fixtures/proposal_demo/main.py`만 읽고 import 없이 소스 목록을 분석한 다음,
시스템 임시 폴더에 새 `authzest-fixture-*` 폴더를 만듭니다. 정확한 diff·제안 ID·복사본 위치·검증 계획을
출력합니다. 표시된 `apply <proposal_id>` 전체 문구를 입력해야 해당 제안을 승인합니다. Enter/잘못된
문구는 거절, `cancel`·EOF·입력 중 인터럽트는 취소입니다. `--yes`나 임의 대상 경로 인자는 없습니다.
터미널 텍스트/JSON은 이스케이프하며 결정은 호출자 입력이지 사람의 신원을 인증한 기록이 아닙니다.

적용 성공 후에는 복구할 정확한 전후 텍스트·해시를 보여주고 `restore <proposal_id>`로 별도 승인을 받습니다.
Enter는 적용한 상태를 유지합니다. 이후 감지된 편집이나 같은 내용의 다른 파일로 교체된 경우 복구를
거부합니다. 원래 fixture로 되돌려 쓰지 않습니다. 거절/취소는 정상 종료, 작업 오류·변경 상태는 실패 종료입니다.
항상 `verification_status: not-run`이며 제공자·하위 프로세스·스캔 대상 코드·설치 hook·검증을 실행하지 않습니다.

## 파일과 현재 세션의 보장 범위

core의 `FixtureApplySession`은 요청/검토/제안을 다시 검증합니다. 선택한 `main.py` 하나와 변경 하나만
허용하며 Git revision 주장은 받지 않습니다. 기존 대상을 받지 않고 직접 새 폴더를 만듭니다.
`parent`는 새 폴더를 생성할 상위 위치만 정합니다.

- 폴더는 비공개 `0700`, `main.py`·`before.txt`·`after.txt`·`record.json`은 `0600`입니다.
  스냅샷은 정확한 UTF-8 바이트이며 CRLF·마지막 개행을 정규화하지 않고 해시를 계산합니다.
- 프로세스 안의 최신 승인/거절/취소가 이전 결정을 대체합니다. 적용 시도 전 결정을 소비하고 임시 쓰기 후
  만료를 다시 확인하며 외부 결정 기록을 받지 않습니다. 거부한 시도를 다시 하려면 새 명시적 결정이 필요하고,
  최종 오류는 해당 세션을 끝냅니다. 적용 완료한 세션에서는 같은 승인을 재사용할 수 없습니다.
- 디렉터리 핸들을 기준으로 연산하며 크기 제한 읽기에서 symlink·hardlink·비일반 파일·권한/식별값 변경을
  거부합니다. 교체 직전에 내용·메타데이터를 검사하고 완전히 쓰고 flush한 임시 파일로만 `main.py`를
  원자적으로 교체합니다.
- 기록에는 제안/결정 식별값·전후 해시·이벤트·결과를 남깁니다. 복구는 현재 파일이 적용 직후의 내용과
  식별값에 일치할 때만 세션이 보관한 원본 바이트로 수행합니다. 자동 rollback으로 후속 편집을 덮지 않습니다.
- `close()`는 핸들만 닫습니다. 복사본·스냅샷·기록은 보존하며 정리 실패 시 임의 이름의 `.stage-*` 파일도
  남을 수 있습니다. 출력한 작업 폴더를 직접 확인한 뒤 필요하면 직접 삭제하세요. 원래 checkout을 reset할
  필요는 없습니다. 임시 저장소는 영구 백업이 아닙니다.

## 실패 의미와 한계

`applied`는 교체가 발생했다는 기록이지 보안 검증 성공이 아닙니다. 복구 후에도 과거 사실로 true를
유지하며 `restored: true`가 원본 복사본 복구를 뜻합니다. 쓰기 후 기록/영속화/읽기 실패를 미변경으로
보고하지 않습니다. `applied-state-unconfirmed`·`*-audit-failed`는 직접 확인해야 하고,
`restoration-state-unconfirmed`에서는 `restored: null`을 사용합니다. 갑작스러운 종료 시 의도만 기록될 수
있으므로 마지막 phase만으로 성공/실패를 추정하지 말고 실제 바이트와 스냅샷을 확인하세요.

이는 **단일 프로세스·독점 쓰기를 전제로 한 fixture 복사 도구**이며 OS sandbox나 범용 패치 실행기가
아닙니다. 원자적 교체는 원자적 조건부 교체가 아니며 비협조적/적대적인 동일 사용자 프로세스는 마지막
검사와 경쟁할 수 있습니다. 작업 도중 복사본을 동시에 편집하지 마세요. 폴더 소유자는 기록을 변조할 수
있으며 서명·신원 인증·재사용 방지 자격 증명이 아닙니다. 재시작/이어하기·자동 crash 복구·파일시스템 전체
트랜잭션·임의 checkout 편집·다중 파일 적용·지속적인 승인 철회 서비스는 없습니다. 기록을 다시 열어도
세션을 재개할 수 없습니다.

실제 Codex 연동·외부 소스 공유 결정·별도 승인한 격리 검증은 후속 #35 작업입니다. 복사본 전용 데모만으로
최종 종단간 완료 기준을 충족하거나 새 릴리스를 발행하지 않습니다.
