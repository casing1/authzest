**Accepted scope (2026-11-24 KST).** This is the course-release target. It replaces the earlier

recorded scope only; the external workflow was delivered and accepted later, as shown below.

## Product and supported release target

AuthZest aims at FastAPI source-based authentication/authorization analysis with AI-assisted
patching. Version 0.1.0 covers **GET object-ownership authorization defects** in one explicitly
selected, self-contained Python application file in another local folder. The user supplies the
policy, because route declarations alone do not say who should be allowed to read what.

| Area                     | Required 0.1.0 behavior                                                                                                                                                                                                                                                    |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Source and setup         | One selected FastAPI application file, in-memory data, explicit app entry and supported pinned dependencies. Initial active environment: macOS arm64, Python 3.12 source installation and Docker Desktop.                                                                  |
| Authentication boundary  | Use the reviewed synthetic or specified identity setup. Check anonymous denial when the policy requires it. A real login system and real identities are out of scope.                                                                                                      |
| AI artifacts             | The model writes a new bounded HTTP PoC request (data, not code) and the replacement source. Picking a registered after-template does not count as generation.                                                                                                             |
| Independent verification | Run the exact before and after source in isolated A guests and capture bounded HTTP observations through trusted B observers. The expected policy answers stay on the host, apart from the AI output.                                                                      |
| Correction and recovery  | Review the exact diff, apply only after current explicit decisions, verify the private copy, then separately approve the final single-file original application. Preserve backup, refuse changed originals and support inspected recovery without overwriting later edits. |
| Presentation             | CLI progress and a complete result JSON. External-workflow GUI scope is saved-result viewing, with unsupported, not-run, unknown, failure and recovery states visible.                                                                                                     |

Keep 4–8 independently reviewed cases: one designated regression, normal owner access, non-owner
denial, anonymous denial where it applies, and either a public route or a reviewed reason why none
applies. Record who wrote the cases, the identity assumptions and the expected answers before and
after the repair. The concrete answers and the image and runtime inputs are reviewed before an actual
trial. Matching observations cover these cases only, not the whole application.

## Deferred work

- General FastAPI vulnerability analysis and JWT, OAuth, login, session or identity-provider flaws.
- Multi-file/package/`src` layouts, project dependency installation, databases and external services.
- Other HTTP methods, arbitrary request scripts and execution of model-authored Python/pytest PoCs.
- External active-GUI control, expanded native/cross-platform active runtime, extra adapters and
  comparative benchmark expansion.

The delivered fixed demonstration, v1.0 proposal path, v1.1 test interface and T/A/B foundation stay
as they are, with their own limits. The HTTP-data-only A/B route needs its own request, profile,
result and operator contracts, which this freeze did not implement. Old requests are not converted
to fit that route, and no T IDs, counts, pytest results or live evidence are invented for it.

## Current state and completion gates

At the freeze, baseline `59ed05b` had external proposal capture, private-file APIs,
supplied-comparison contracts, sealed inputs and unexecuted guest and create-plan foundations. The
repository images were unbuilt, and the external operator, the final original write and installed
live acceptance were unfinished. Earlier packaged demonstrations are separate evidence; they did not
run this new mode.

**Progress (2026-11-25 KST).** PRs #217–#219 added the direct A/B phase, `repo-fix`/`repo-restore`, original application with backup, metadata preservation and recovery, the runtime setup script, the demo app and saved-result viewing. The A/B images were built, and the private profile was checked read-only against Docker Desktop 29.9.3. From the source checkout, `gpt-5.6-sol` produced a PoC equal to the designated regression and a repair. The before check matched all 5 reviewed before answers, which reproduces the defect, and the after check matched all 5 after answers. Every guest was removed, and the original was written with a backup. `repo-restore` then refused a later user edit and restored the original bytes once that edit was removed. The apply-time edit-conflict refusal is covered by regressions only. The five demo cases were drafted by the assistant and accepted by the maintainer on 2026-11-25. A wheel built from the PR #219 head `c98bd59` was then installed into a fresh virtual environment and run from site-packages on a fresh demo copy. `gpt-5.6-sol` again produced the regression PoC and an owner-check repair. Before and after each matched 5/5, every guest was removed, the original was written with a backup and the installed `repo-restore` restored it. The saved result opened in the dashboard viewer with the rebuilt diff. Later review fixes changed only the result viewer and its tests, not the `repo-fix` runtime. On 2026-11-27 a second, structurally different example (`examples/external_orders_app`: a `Depends` user, a support role and a 404 that must stay) passed the same way from main `06804b3`: the regression PoC, before and after 6/6, the original write and `repo-restore`.

## Schedule and submission

The official course deadline is **2026-12-06 23:59 Asia/Seoul**. December 1 is an internal
completion target. It neither promises a release date nor extends the official deadline.

| Date (KST)             | Target                                                                                                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| November 24            | Freeze scope; preserve delivered code and historical evidence.                                                                                                                  |
| November 26            | First actual external end-to-end checkpoint, including approved original correction. If it fails, reassess delivery honestly instead of reporting a simulated flow as complete. |
| November 27–December 1 | Resolve observed failures, verify recovery and freeze the demonstrable feature set.                                                                                             |
| December 2–5           | Fresh installation, actual demo/screenshots, README/translations, attribution/license audit and source ZIP verification. No feature expansion.                                  |
| December 6             | Submit with time for final error handling before 23:59.                                                                                                                         |

Submission needs the public repository URL and the source ZIP of the submitted revision. The root
README must explain the purpose, exact support, installation and execution, the actual demo with
screenshots, how to read results, limitations, references and license. Reused code must name its
source and license; the project's MIT label does not replace that attribution. A stable tag can
identify the submitted revision, but the course does not require one. For team work the notice asks
for Git participation records; it sets no personal commit quota.
